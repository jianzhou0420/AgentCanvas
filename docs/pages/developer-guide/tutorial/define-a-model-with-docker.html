Define a Model with Docker

Container Launch — one ClassVar turns a nodeset into a docker-served model

Some models can't be expressed as a conda environment at all: a compiled C++ world with its own build system (ORB-SLAM3), a GPL codebase that must stay out of the framework's process and env (pySLAM), a stack that insists on its own OS packages. For these, declare a docker image instead of an interpreter — Container Launch (design doc, ADR-server-005). Everything else about the nodeset is ordinary: nodes are written as in Define a Node, the class as in Define a NodeSet, and the canvas sees auto-generated proxy nodes exactly as for a conda-served nodeset. Prerequisite: a rootless docker daemon (Installation §2.6).

1. When Docker, not conda

Server mode has two launch vehicles; pick per nodeset:

SituationDeclareVehicle
Model installs cleanly into a conda env (its own torch, pinned Python)server_pythonNative Launch — host subprocess
Model needs a compiled system stack, its own OS packages, or license isolation (GPL out of the framework env)server_imageContainer Launch — docker run

When both are set, server_image wins. Either way the container/subprocess serves the same protocol (/manifest · /call/{fn} · /health · /mcp), so nothing downstream changes — and the framework is never baked into the image: the repo is bind-mounted read-only at /opt/agentcanvas-workspace and the container runs the stock auto_host from that mount. A framework upgrade never requires an image rebuild.

2. Folder layout

An image recipe is a sidecar, so the nodeset is a folder package (see Define a NodeSet §1). Everything you author lives in the folder; the built image lives in the docker store, weights under data/, outputs under outputs/:

workspace/nodesets/model/model_mymodel/
├── __init__.py            # nodes + nodeset class + all Container-Launch ClassVars
├── _backend.py            # (optional) in-container logic, imported by the nodes
└── docker/
    ├── Dockerfile         # model deps + requirements-serve.txt — never framework code
    ├── build.sh           # builds into the rootless store
    ├── requirements-serve.txt
    ├── patches/           # (optional) build fixes applied to the upstream clone
    └── weights/           # (optional) download scripts + README — not the weights themselves

3. The Dockerfile contract

The image carries the model's own world plus the small serve set — nothing else:

# workspace/nodesets/model/model_mymodel/docker/Dockerfile
FROM ubuntu:22.04

# 1. The model's own world — compilers, libs, the model stack itself
RUN apt-get update && apt-get install -y --no-install-recommends \
        python3 python3-pip git cmake build-essential \
    && rm -rf /var/lib/apt/lists/*
# ... clone / build / install your model here ...

# 2. Serve deps — lets the stock app.server.auto_host run from the repo mount
COPY requirements-serve.txt /tmp/
RUN pip install --no-cache-dir -r /tmp/requirements-serve.txt

# 3. Build-time smoke — the import your nodes rely on must resolve
RUN python3 -c "import mymodel; print('binding OK')"

# No ENTRYPOINT, no CMD, no framework code. The command comes from the
# framework at run time; the framework comes from the read-only repo mount.

Three rules, each learned the hard way (they are pinned in the design doc's deviations):

  • No framework code in the image. requirements-serve.txt (fastapi / uvicorn / httpx / msgpack / numpy / pydantic / pyyaml; optional mcp) is the only framework-adjacent content — copy the reference file from agentcanvas/backend/requirements-serve.txt into docker/.
  • Prefer no ENTRYPOINT. An entrypoint that mutates the environment (pyenv/conda activation) wipes the framework's -e PYTHONPATH injection — the container then dies with No module named 'app'. If the image must have one, save and restore PYTHONPATH inside it.
  • Mind the image's USER. Under rootless docker, container root is the invoking host user, but a non-root image user maps to a foreign subuid that cannot write host-owned rw mounts. An image that drops to a non-root user needs server_container_user = "0:0" (§4) — this loosens nothing.

build.sh targets the rootless daemon explicitly, so it works from any shell:

#!/usr/bin/env bash
# docker/build.sh — targets the rootless daemon regardless of shell context
export DOCKER_HOST="unix:///run/user/$(id -u)/docker.sock"
docker build -t agentcanvas/mymodel:latest "$(dirname "$0")"

4. The nodeset class

One ClassVar is the whole trigger; the rest of the family tunes the container. Note the two-import life of this module: the backend imports it on the host during discovery (declarations only — model imports must be lazy), and the stock auto_host imports it again inside the container, where the lazy imports resolve and the nodes actually run.

"""MyModel NodeSet — served via Container Launch.

Load:  POST /api/components/nodesets/model_mymodel/load
"""

from __future__ import annotations

from typing import Any, ClassVar

from app.components import BaseCanvasNode, BaseNodeSet, PortDef

_SESSION = None  # module-level: the container process is long-lived


class MyModelInfer(BaseCanvasNode):
    node_type = "model_mymodel__infer"
    # ... ports and identity as in Define a Node ...

    async def forward(self, inputs: dict, ctx: Any) -> dict:
        import mymodel  # lazy: resolves only inside the container
        ...


class MyModelNodeSet(BaseNodeSet):
    """MyModel via Container Launch."""

    name = "model_mymodel"
    description = "MyModel inference nodes"

    server_image = "agentcanvas/mymodel:latest"  # <- the whole trigger
    server_image_gpu = True                      # CDI; one CPU-degrade retry
    server_mounts: ClassVar[dict[str, str]] = {
        "data/models/mymodel": "/opt/weights:ro",  # missing ro -> skipped (warn)
        "outputs/mymodel_runs": "/opt/out",        # missing rw -> created
    }
    # server_container_python = "/opt/venv/bin/python"  # image with a baked venv
    # server_container_user = "0:0"    # image whose USER is non-root + rw mounts
    parallelism = "replicated"         # stateful session: one container per worker

    def get_tools(self) -> list:
        return [MyModelInfer()]

The Container-Launch ClassVar family:

FieldDefaultWhat it decides
server_imageNoneDocker image tag. Setting it auto-routes the nodeset to server mode on Container Launch; takes precedence over server_python. The image must already be in the rootless store — a missing image fails the load with an explicit "build it" error, nothing is auto-pulled.
server_image_gpuFalseRequest the GPU via CDI (--device nvidia.com/gpu=all). A failed GPU start degrades once to a CPU start of the same image.
server_mounts{}Extra binds, {host_path: "container_path[:ro]"}. Host paths may be absolute, ~-prefixed, or repo-root-relative. Missing ro path → skipped with a warning (an optional weights dir degrades that capability, not the start). Missing rw path → created (it is an output drop; skipping would strand writes inside the container).
server_container_python"python3"Interpreter inside the container. Images with a baked venv must point at its exact python.
server_container_userNonedocker run --user override. Set "0:0" for images whose USER is non-root and that write rw mounts (§3); pair with a HOME entry in server_env when the image's paths assume the baked user's home.
server_env{}Env vars injected into the container (-e) — model knobs, HOME, cache paths.

5. Build, load, verify

# 1. build the image into the rootless store (repeat only when the recipe changes)
bash workspace/nodesets/model/model_mymodel/docker/build.sh

# 2. load — server_image auto-routes the nodeset to server mode, Container Launch
curl -X POST http://127.0.0.1:8000/api/components/nodesets/model_mymodel/load

# 3. see it running: deterministic name, protocol port on 127.0.0.1
docker ps --format '{{.Names}}'   # -> ac_auto_model_mymodel_<port>

What the load does, in order: checks the image exists → reaps any stale container of the same name → starts a foreground docker run --rm --init as a direct child (so health polling and process cleanup work exactly as for a conda subprocess) → waits for /health → fetches /manifest → generates one proxy node per function. From here on, everything is the ordinary server-mode feature set: canvas wiring, env-panel bridge, batch eval with per-worker containers (parallelism = "replicated"), the /mcp projection. Node code that must call back into the executor reaches it automatically — loopback executor URLs are rewritten to host.docker.internal at assembly time.

6. Checklist

  • Folder package with the recipe in docker/; weights scripts in the folder, weight files under data/ via server_mounts
  • Image = model deps + requirements-serve.txt; no framework code, no ENTRYPOINT/CMD
  • Build-time smoke RUN python3 -c "import …" so a broken binding fails the build, not the first load
  • Model imports lazy (inside forward() / initialize()) — the module must import cleanly on the host during discovery
  • Non-root image USER + rw mounts ⇒ server_container_user = "0:0" (+ HOME in server_env)
  • Baked venv ⇒ server_container_python points at its exact interpreter
  • Stateful session ⇒ parallelism = "replicated" and a module-level session singleton, torn down in shutdown()
  • Worked examples: model_orbslam3 (minimal, CPU, root image) and model_pyslam (GPU, baked venv, non-root image — the full ClassVar family in use)
