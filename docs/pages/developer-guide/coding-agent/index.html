CAN：Coding Agent as Navigator — 项目计划（讨论稿）

把「coding agent 能导航」从一个 Claude Code 轶事，变成开源框架 + 开源小模型上的可复现科学 —— 目标 ICLR 2027。

现状：本仓库的 beta-coding-agent 用 Claude Code（世界上最强的闭源 agent 框架）证明了 vanilla coding agent 能做 zero-shot R2R-CE——这是存在性证明，但闭源、昂贵、不可消融。本计划把同一命题搬到开源可控的整套栈上：SWE-agent 系框架做 harness、Qwen3.5-9B 级开源小模型做大脑、AgentCanvas 做环境与评测底座，系统性回答「coding agent 的哪些器官能迁移到具身导航、在多小的模型上还成立」。本文整合了 ../NavHarness/docs 的全部遗产（旧路线的方法论保留、定位翻新，见 §4），按 Motivation（§2）→ Method（§6）→ Plan（§8）组织，§10 是待你裁决的决策点。本目录已加入 .gitignore（本地可见、永不发布）——未投稿的想法不上公网。

工作代号 CAN（Coding Agent as Navigator）。取双关：论文可以直接问 "Can coding agents navigate?"——与 2026 年的 Can Coding Agents be General Agents? (26.04) 形成文献对话（他们在 ERP 上给出否定证据，我们在具身导航上给出工程化的正面回答）。命名候选见 §10。

1. TL;DR：一句话与一张图

一句话：不要给导航造第 N 个 bespoke harness——把导航 episode 装进 coding agent 的原生世界（一个文件系统 + 一个 CLI），让标准开源 coding-agent 框架原样开工；然后用开源小模型阶梯（Qwen3.5-2B/4B/9B → 35B-A3B）做三件闭源 agent 做不了的事：逐器官消融（文件记忆 / code-as-action / 验证门 / 自主度）、规模曲线（harness 增益 vs 模型大小）、零成本复现（全栈本地、$0 API）。

2. Motivation：四层动机

2.1 存在性已证明，科学还不存在

2026 上半年，「harness 决定 zero-shot VLN 表现」被至少四个互相独立的系统反复证实——但每一个都是不可比、不可归因的 artifact：

系统形态成绩（R2R-CE val_unseen）问题
AgenticNav (26.06, SJTU+华为)bespoke 四工具 harness（query_depth / recall / move_to / stop）GPT-5.5：55 SR / 48.4 SPL（100 集，zero-shot SOTA）；但开源 Qwen3.6-27B 骤降到 35 SR不是 coding agent（无文件系统、无代码执行）；memory 机制交代不清（见 §6.5）；小模型崩
SpaceVLN (26.06)bespoke 空间认知记忆 harnesszero-shot（数字待复核）又一个不可比 artifact
组内 beta-coding-agent（zh-2）真 coding agent：Claude Agent SDK + MCP 三工具 + skillsrand100 协议就绪，10 集校准数据见 monitor §5闭源模型 + 闭源 harness：不可消融、不可复现、订阅计费、无法回答「为什么 work」
qwen-robotnav (26.06, 阿里)训练的 nav FM + 配套 harness（robotclaw）R2R 72.1 / RxR 76.5（trained，非 zero-shot）15.6M 样本、数千 GPU 时——另一条赛道

缺的东西非常具体：一个开源、可控、便宜的 coding-agent 导航栈，加上一套「哪个器官贡献几分」的归因实验。没有它，「coding agent 能导航」永远是轶事；有了它，师兄的 Claude 结果、AgenticNav 的 55 分、qwen-robotclaw 的产品设计，全都获得一个可以解释的机制坐标。

2.2 理论张力：coding agent 的护城河在导航正好缺一半

我们在 zh-4（概念篇）里论证过：coding agent 的强大来自两点——开放行动空间（运行时自写工具）与密集客观反馈（编译器/测试/栈回溯）。搬到 VLN，NavHarness 时期总结的「三大扭曲」恰好各打一半：

VLN 扭曲（NavHarness 7/08 讨论）对 coding agent 意味着什么CAN 的机制回应
① 没有 live verification（走错了环境不报错，直到 STOP 后才算分）反馈护城河失效——这正是 ERP 论文说的「反馈不对称」领域，coding agent 会退化 + 过度自信验证工程（§6.7）：确定性 guards + STOP 门 + agent 自写 checks——把「写测试」的本能移植过来
② 观测是图像，上下文爆炸比代码狠得多coding agent 的上下文管理组件（压缩/外置/检索）正好是解药文件系统当记忆（§6.5）：观测自动落盘，逐出上下文是无损的（磁盘上还在，按路径可取回）
③ STOP 是胜负手等价于 coding agent 的「什么时候敢说完成」——已知其最大失败模式（自报成功）pre-stop 强制核对 hook（§6.7）——直接检验 NavHarness 预注册的 H4（verifying-stop 假说，+1~6pp）

所以科学问题不是「coding agent 能不能导航」（beta 已证明能），而是：coding-agent 配方的哪些器官在反馈稀疏的具身域仍然做功、哪些必须重新工程化、在多小的模型上这套配方还成立。这是一个「迁移解剖学」问题——恰好只有开源栈能回答。

2.3 为什么是开源小模型：科学性 + 一个可赢的数字

  • 可复现性碾压：Claude/GPT 结果依赖闭源模型的当月版本；Qwen3.5 权重冻结在 HF 上，全栈本地跑，$0 API、单卡 5090 复现。这比 NavHarness 时期设想的「$100 可复现」还激进一档，是审稿硬通货。
  • 时机刚好：Qwen3.5 小模型系（2026-02）是原生多模态（早期融合，图像+视频），262K 上下文全系标配，9B 的 MMMU-Pro 69.2 反超 Qwen3-VL-8B（56.6）——「一个 9B 模型同时当眼睛和大脑跑 agent 循环」在半年前还不成立。另有 Qwen3.5/3.6-35B-A3B（MoE，3B 激活）做阶梯上端，量化后单卡可跑。
  • 有明确的锚点可打：AgenticNav 的 backbone 消融给了开源模型在 bespoke harness 里的水位——Qwen3.6-27B = 35 SR。CAN 的可赢主张之一：9B 模型 + coding-agent 工作区 ≥ 27B 模型 + bespoke 工具 harness。若成立，这是「harness 补偿模型规模」迄今最锋利的具身证据；若不成立，规模曲线本身就是发现（§3 H6）。
  • 小模型是 harness 科学的显微镜：大模型把 harness 缺陷「脑补」掉了；小模型对接口设计极端敏感（SWE-agent 的 ACI 论题、NavHarness 的「小模型往 workflow 挪」判断）。效应量在小模型上更大、更可测。

3. 研究问题与预注册假设

RQ1（headline）：标准开源 coding-agent harness 能否让开源小模型成为有竞争力的 zero-shot 导航员？
RQ2（解剖）：coding-agent 配方的哪些器官（文件记忆 / code-as-action / 验证门 / 自主循环）各贡献几分？哪些在具身域失灵？
RQ3（规模）：harness 增益如何随模型大小变化？自主度上限如何随模型大小移动？
RQ4（机制）：文件系统式记忆（内容寻址：grep 自己的笔记）是否优于 AgenticNav 式索引召回（位置寻址）？——把 NavHarness 7/08 的机制批判变成实验。

预注册假设（继承 NavHarness 的预注册文化，证伪条件先写死）：

H2记忆消融单调：无记忆 < 纯上下文 < 文件+grep；且内容寻址 > 位置寻址召回（≥+3 SR）文件记忆不增益
H3code-as-action（允许自写脚本/宏）相对固定 CLI：SR 不降且 LLM calls/ep 显著下降（CodeAct 效应迁移）calls 不降或 SR 大跌

6. Method：CAN 系统设计

6.1 设计原则：把环境搬给 agent，而不是把 agent 搬给环境

AgenticNav、qwen-robotclaw、SpaceVLN、NavHarness exp01/02——所有前人路线都在为导航造专用 harness。CAN 的第一性主张反着来：coding agent 已经拥有地球上被打磨得最狠的 harness（循环、上下文管理、文件记忆、工具校验、子进程），它唯一的要求是世界长得像「文件系统 + shell」。那就把 episode 渲染成一个文件系统 + 一个 CLI。做到这一点，整个 coding-agent 生态（任何 SWE-agent 系框架、任何 LM、未来的任何改进）对导航零改造可用——这是比任何单点技巧都值钱的接口主张。

nav observe拍一帧 → 写 obs/step_N/，stdout 打印 state 摘要 + 图片路径只读，不推进模拟；对应 beta 的 observe
nav step 1 1 2 ...批量离散动作（0=STOP, 1=前进0.25m, 2=左转15°, 3=右转15°），单次 ≤50对应 beta 的 step；返回执行数/剩余预算/episode_over
nav look前/右/后/左四视图落盘，恢复朝向（耗 24 步转向预算）对应 beta 的 look_around
nav stop发起 STOP —— 在 A3+ 配置下要过验证门（§6.7）成功判定要求 3m 内主动 STOP，driver 永不强停（beta 纪律不变）
nav status步数、预算、动作史尾部纯读
nav recall --step N按索引取回历史观测（只在 H2 对照臂开启）复刻 AgenticNav 的位置寻址接口，与 grep 内容寻址对打

关键性质：观测历史天然全量持久、天然内容可检索（agent 对自己写的 notes.md 用 grep，就是内容寻址记忆），上下文逐出天然无损（把旧观测从上下文里换成一行路径指针，需要时 agent 自己 cat 回来）——NavHarness exp01 最担心的「有损压缩把关键细节压没」在这个基座上是个结构性非问题。

6.4 ANI：agent-navigation interface（SWE-agent ACI 论题的迁移）

SWE-agent 的核心发现是「接口要为模型设计」（换工具格式，SWE-bench 6.7%→68.3%，出自 harness 综述精读笔记）。导航侧对应三个设计轴，全部进消融：

轴选项默认（v1 赌注）
感知渲染(a) 图像直入上下文（Qwen3.5 原生多模态）；(b) 文本化——nav describe 用同一模型的 captioning 子调用把帧压成文字（模型当自己的眼睛，harness 决定何时看）；(c) 混合：当前帧图像 + 历史帧文字(a) 图像直入 + 历史帧降级为路径指针——Qwen3.5 选型就是为了这个；(b)(c) 做 A5 消融臂
动作批量单步 vs 批量（≤50）；批量省 calls 但盲走风险↑批量默认、系统提示约束「转弯后必须重新观察」
上下文预算每步进上下文的 token 上限；旧观测 TTL（保留最近 K=2 帧图像，更早的换路径指针）；notes.md 摘要注入预算 6k tok/轮（9B 的 262K 上下文富余，但成本/延迟仍要报告——继承 exp01 纪律）

6.5 记忆 = 文件系统：把 AgenticNav 批判变成实验

NavHarness 7/08 文档对 AgenticNav memory 的批判（§9.8）值得原样引用：模型推理在语义空间（「我要再看看刚才那个路牌」），而它的 recall(p,k) 接口要求输出离散索引（步号/视图号）——中间缺「内容→索引」的映射，是接口层 type mismatch；消融里 recall 只值 4 分可能正因如此。CAN 的文件系统记忆给出结构性修复：

  • agent 写笔记时自己完成了语义标注（"step 42: 厨房入口，左侧有红色冰箱" 写进 notes.md）；
  • 检索时 grep -i "厨房" notes.md ——内容寻址，零新机制，就是 coding agent 的日常动作；
  • H2 对照臂：同一系统只把 grep 换成 nav recall --step N 位置寻址 → 差值就是「寻址方式」的因果贡献。这是「我们的坐标系能产生别人产不出的实验」的现场兑现（组会调整②里许过的愿）。

6.6 Code-as-action：coding agent 的定义性能力

L2+ 档位允许 agent 往 scripts/ 写并执行代码（沙箱内、只许 import 白名单 + 调 nav）。预期用法：scan.sh（look + 批量重命名视图）、corridor.py（循环「前进→读 clearance→低于阈值停」）、turn_to.py（角度→动作序列换算）。CodeAct 在工具基准上的结论（占优 + 轮次 −20%）预测 H3：calls/ep 显著下降——对小模型这直接等于「把控制流从脆弱的逐 token 决策卸载到确定性程序」。这是「coding agent as navigator」里 coding 两个字的实义所在：beta 版被剥掉的能力（tools=[]），CAN 把它还回来并单独计价。

6.7 验证工程：给反馈稀疏域造反馈

层机制性质
V0 确定性 guards碰撞连击告警（clearance+动作史，driver 侧注入 stdout）；打转检测（位姿窗口内位移≈0 → 提醒）model-free、零成本，全档默认开
V1 STOP 门nav stop 第一次被扣下：强制 nav look + 打印指令终点子句 + 要求 agent 对照四视图逐条核对后再次确认beta 已有雏形（STOP 确认门）；升级为结构化 checklist；H4 的检验点

立场声明（相对 NavHarness 的转变）：NavHarness 7/08 主张代理信号尽量 open-loop（只记录不干预），因为它想测「裸模型」。CAN 的研究对象就是 scaffold 本身——所以验证信号光明正大地闭环，但每一层单独消融、单独披露。两个立场服务于不同的问题，论文里一句话说清即可。

6.8 自主度旋钮 × 模型阶梯

档循环形态给谁
L1 分相 workflowdriver 按固定相位轮询（OBSERVE→UPDATE-NOTES→DECIDE→ACT），每相模板化 prompt、限定合法动作，必要时 vLLM structured output 约束解码2B/4B 保底档——NavHarness「小模型往 workflow 挪」的实现
L2 引导 ReAct自由 bash 循环 + 纪律性系统提示（先看后动 / 每 K 步必写 notes / 预算提醒）+ V0-V29B 主力档（v1 默认）
L3 自由 bashmini-swe-agent 原样，只给 README.md，其余全靠 agent 自己发现上限档：35B-A3B / Claude 参照——也是「vanilla 迁移」的哲学纯度档

H5 的交互预测：每个模型档在不同的 L 档见峰。主图（论文 Figure 1 候选）：x=自主度 L1→L3，y=SR，线=模型大小，Claude 参照线封顶——一张图讲完「自主度必须随规模缩放、harness 结构在哪个规模救得了谁」。

基座选型：mini-swe-agent 而非 full SWE-agent——① ~100 行核心，改造与审计成本最低；② 纯 bash、不依赖模型的 function-calling 能力（小模型的工具调用格式错误是著名死因，bash-only 直接绕开）；③ LiteLLM 后端任意换。full SWE-agent 的 ACI 工具箱（文件编辑器等）作为 L2 档的参考设计来源。

7.4 失败归因（NavHarness 协议原样移植）

六类 taxonomy：false_stop / stuck_loop / subgoal_drift / cross_step_forget / recognition_fail / model_other；100 个失败集双标注、自动 tagger 对人工 κ≥0.6 才可上规模。CAN 额外多一层免费证据：agent 的 notes.md 和 checks.md 本身就是失败时的第一人称口供——归因不用全靠回放猜（这是文件系统记忆送的分析红利）。beta monitor §5 的 Claude 失败类型学做跨模型对照：小模型的失败分布 vs Claude 的失败分布，差异本身是 RQ3 的证据。
