.claude 工具生态与文档站构建方式：能为 CAN 复用什么

拆解本仓库两样可以直接为 CAN（Coding Agent as Navigator）复用的资产——一套把 skill 当"目录"来写的 slash-command 技能生态，和一套零依赖、纯 Python stdlib 的手写 HTML 文档站构建系统。

本页回答三个问题：① .claude/ 里哪些 skill 值得学、真正该学的其实是结构而非某条命令（§1）；② 这个 doc-site 到底怎么搭起来的、为什么零依赖（§2）；③ 这套格式怎么被 CAN 利用、下一步走哪条路线（§3）。系列前篇：CAN 项目计划。本页本身就是用这套格式写成的——是"利用格式"的第一次实操。

三句话结论：① 最值得学的是技能的组织结构——architect/myloop 把一个自改进的 agent-design 搜索循环拆成五相 + 11 个结构化记忆文件 + schema 契约，几乎可以照搬到 CAN 的 navigator 设计搜索。② Doc-site 是 HTML-first + 零依赖：内容只写在 <main>，导航/面包屑/TOC/搜索全由 _lib/ 的 Python 再生成，.gitignore 直接当"公开/私有"开关。③ 两样都能低成本复用。

1. 值得学习的 Skill：技能不是一个文件，是一个目录

.claude/ 分三层：commands/（55 个 .md，每个注册成一个 slash 技能）、standard/（9 份被多个技能引用的可复用规范）、tutorials/（5 份教学文档，给人读、不给 agent 跑）。真正的价值在复杂技能的组织方式，而不是某一条命令。

1.1 优先研究清单

★ architect/{myloop, adas-subagent, aflow}

自动化 agent-design 搜索循环（旗舰）。myloop 是知识蒸馏式编排器：每轮 THINK（提出 K 个 ExperimentSpec）→ CRITIC（逐 spec 预判病理）→ EXPERIMENT（Python wrapper 并行跑评测）→ DISTILL（一次看齐所有 spec 出结论），外加不每轮跑的 REFLECT 元阶段做"搜索空间制图"，把 THINK 从局部最优里拽出来。11 个结构化记忆文件，schema 是唯一真源。

.claude/commands/architect/

★ gaps/{ground, problem, solution, result}

Ground·As-is·Problem·Solution——动手前把改动想清楚的范式（旗舰）。强制先把"现状"锚定到 file:line、把"问题"逼到根因，再谈方案。四个子技能各写一份活文档的一个"band"，人类在每段之间留在回路里。专治"还没搞清问题就先跳到方案"。可迁移到任何设计决策。

.claude/commands/gaps/

implement-graph + grill-implement

把一篇论文 + 它的 repo 移植成一张 AgentCanvas graph，再逐条消除移植版与上游的差距。正是把 VLN / 导航方法搬进平台的标准工作流——和 CAN 直接相关。

.claude/commands/

docs/*  &  experiment/*

docs/：记录架构决策（ADR）、整站通读、写 method-nodeset 页、更新文档。experiment/：后端 JobScheduler 的瘦客户端，提交 graph 评测 / 查状态 / 取消——myloop 的 EXPERIMENT 相就跑在这层上。

.claude/commands/{docs,experiment}/

其余是会话级基础设施：overview（重建项目总览）、memory/hygiene（清理自动记忆）、todo/*、callitaday、translate-readme——单看不惊艳，但撑起了整套工作流的连续性。

1.2 真正该"偷"的是这几个模式

技能本身会随项目变，下面这套组织方式才是可以直接搬到 CAN 的。

模式做法
skill = 目录README（心智模型）+ understand（会话开场阅读清单）+ schemas（契约 / 唯一真源）+ 每个阶段一个 .md + data/（种子知识）+ lib/*.py（确定性辅助）+ config.yaml（文件清单）。只有 .md 会注册成技能。
_common/变体之间共享的子技能（implementer / evaluator / understand / files-contract），对技能本身做 DRY。
阶段 + schema每个阶段是一次子 agent spawn，带类型化的输入输出契约；编排器只负责串阶段、原子提交。
结构化持久记忆append-only 的 knowledge / experience、独立的 hypotheses、每轮 record、以及 trace / lineage 汇总表——让循环"越跑越懂"。
standard/ + tutorials/可复用风格规范（被多技能引用）与教学文档分离：技能是给 agent 跑的，教学是给人读的。

2. Doc-Site 怎么搭：HTML-first · 无框架 · 纯 stdlib

没有 markdown 源、没有构建框架、没有 npm。全部构建逻辑是 docs/_lib/ 里几个纯标准库 Python 脚本，产物直接部署到 GitHub Pages。

2.1 核心思想：内容与外壳分离

每个页面里你手写的只有 <main class="doc-body"> 内部的内容。顶栏、侧边导航、面包屑、右侧 TOC、页脚这些外壳（chrome）不是手写的——它们由 _wrap_handwritten.py 从 _layout.py + _nav.py 再生成并写回。

  手写 <main>            _wrap_handwritten.py            产物
  ─────────────      ───────────────────────      ─────────────────────
  pages/**/*.html  →  抽 title + main + 更新时间  →  完整 html（仅变更才写）
  （只有内容）         剥旧外壳                       + nav.json
                      经 _layout.render() 重渲染      + search-index.json
                                                          │
                                                          ▼
                                            nav.js 按 nav.json 客户端渲染
                                            tab / 侧栏 / 搜索

2.2 _lib/ 里都有什么

  • _wrap_handwritten.py幂等再包裹器：读每页的 <title> + <main> + last-updated，剥掉旧外壳，用 _layout.render() 重渲染，只在内容真变了才写回（保持 mtime 稳定，dev server 不会把自己的输出当成新改动死循环）。顺带生成搜索索引和 nav JSON。
  • _layout.py共享外壳：一个 PageMeta dataclass + render()。页面结构是 顶栏 → 三栏网格（左侧栏 | main | 右 TOC）→ 页脚。
  • _nav.py / _tab.json声明 tab 和 section 列表，构建 nav.json。加一个 section 就是往列表加一条 dict。
  • _serve.py / run_dev.sh纯 stdlib dev server，监听 mtime，用 SSE 做热重载，改动约 500ms 进浏览器。

2.3 两个聪明的机制

客户端渲染导航：页面里只烘焙空的侧栏/tab 壳子，导航树由 nav.js 从生成的 nav.json 客户端渲染。结果——加 / 删 / 改名一个页面，git 里只动它自己那一个文件，不碰任何兄弟页、不碰导航产物。

.gitignore = 可见性开关：wrap 过程对 pages/ 跑 git check-ignore：被 ignore 的页从公开的 nav.json / search-index.json 里剔除，但保留在 *.local.json 双胞胎里，由 dev server 本地顶替。所以私有 section 本地可见、永不泄漏到线上——本目录 coding-agent/ 就是靠 .gitignore:159 这么私有的（本页也一样）。

2.4 写页面的约定

来自 standard/html-authoring.md：<header class="page-header"> 包 <h1> + <p class="tagline">；一段 <p class="lede"> 导语；带编号的 <h2 id="1-...">（内含 <span class="num">，右 TOC 就是从这些 id 生成的）；代码块用 Pygments 预高亮的 <pre class="hl">（绝不上客户端高亮器）；页内用相对链接；提示块用 .callout note/warn/success，卡片用 .cards + .card，编号清单用 .numbered-list——这些组件站点 CSS 已内建，页面通常不需要自己写 <style>。改了 nav/layout 后跑一次 python3 docs/_lib/_wrap_handwritten.py 把新外壳刷到所有页。

3. 这个格式怎么被我们利用

3.1 为什么它对 CAN 特别顺手

  • 零依赖（纯 stdlib）→ 整个 docs/ 骨架可以原样 vendor / 复制，不用维护 node_modules。
  • 内容 / 外壳分离 → 写作者只碰 <main>，不用管布局。
  • gitignore 私有区 → 研究笔记留在本地，对外文档照常部署，一条 .gitignore 搞定。
  • 自动导航 / 面包屑 / TOC / 搜索 → 没有手工维护成本。
  • 已经能部署到 GitHub Pages → CAN 的项目主页几乎是现成的。

现状：你已经在用它了——coding-agent/ 下已有 zh-1-project-plan、zh-2-git-workflow、zh-2-swe-agent-anatomy 三页（gitignore 私有），本页是第四页。

3.2 下一步的候选路线

路线做什么成本
A把这份记录落成 doc-site 页（本页即是）——按站点格式写、跑 wrap，顺便把"复用格式"亲手走通。低 · ✓ 已完成
C先用 gaps 范式把 CAN 的 Ground / As-is / Problem / Solution 写成活文档，避免过早跳到方案。是 B 的理想前置。中 · 主要是想清楚
B以 architect/myloop 为蓝本起一个 can-loop 技能：五相 + schema + 种子知识，搜索 navigator agent 设计。研究价值最高、也最重。高 · 需先定评测/搜索空间
D把 docs/ 抽成独立的 CAN 文档 repo，改 _site.json + _nav.py 的 tab，独立部署。等 CAN 要脱离 AgentCanvas 单独发布时再做。低-中 · 主要是配置

建议顺序：A 已随本页完成 → 先 C（用 gaps 框清 CAN 的问题）→ 再 B（照 myloop 搭搜索循环）；D 等 CAN 要独立发布时再说。具体走哪条，你定。
