Harness 隐性差异：vision 上下文管理（以及为什么它污染对比）

这页记录 harness 之间那些不写在 cell 名里、却会影响结论的隐性差异。第一条（已订正一次，见 §4）：视觉历史——原以为「SDK 近窗、mini 全带」；读了 Claude Code 源码后订正为：喂给两者的图大小一样、两者也都全量累积每轮重发，真正的差别只在兜底——SDK 到阈值会整段 compact，mini image_window=0 没兜底 → 撞 32MB。

一句话（已订正）：Anthropic API 默认每轮重发全部历史图片字节，单请求上限 32MB，超了 413。喂给 CC 和 mini 的图大小完全一样（同 env、同帧），而且 CC 源码确认它默认不逐帧淘汰图（applyToolResultBudget 原样透传含图块、时间触发清理默认关、cached-MC ant-only 且只认内置工具不碰 MCP observe()）。所以 SDK 和 mini(image_window=0) 都在全量累积同样的图、每轮重发——差别只在兜底：SDK 到阈值整段 compact 重置，mini 没兜底、一路涨到撞 32MB。已在 harness_inherent.vision_context 里把每条 harness 的兜底策略记下来。

1. 为什么单开这一页

我们的 summary.json 已经记 harness_inherent（auth / thinking / turn_cap）—— 因为这些是「不在 cell 名里、但决定结果」的 harness 固有事实。vision 上下文管理是同一类:两条 harness 给模型的视觉历史不等量,直接影响导航成败,却一直没被记下来。这页 + 新增的 vision_context 字段补上它。

2. 事实层：API 怎么处理图

  • 单请求上限 32MB（标准端点;Bedrock/Vertex 更低),超出返回 413 request_too_large;单图 10MB base64;一次 >20 张图触发更严的尺寸限制。
  • 默认每轮重发全历史。官方 Vision 文档原话:"each request resends the full conversation history. If images are base64-encoded, the full image bytes are included in the payload on every turn." —— API 本身不做任何 vision 裁剪。
  • 交互式 Claude Code 不自动删「用户贴的图」（issue #52224,feature request,已关;只有 /compact、/clear、开新 session）。

注意 #52224 说的是用户贴的图;我们的 observe() 图是经 MCP 回来的 tool_result 图 —— 这一类由 agent loop 管理,行为不同(见 §4)。

4. 订正：CC 并没有在「窗口化」

本节原来的结论错了。原推理：「一集 60 帧 × 1.1MB ≈ 66MB，而 CC 实测 <10MB → 它一定只留了近窗几帧，铁证」。读 Claude Code 源码后确认 CC 默认不逐帧淘汰图，这个「铁证」不成立。

为什么原推理站不住：

  • 同样大小的图喂给两者。CC 和 mini 跑同一个 env、同样的帧，图字节数一样 —— 请求大小差异不可能来自图大小。
  • CC 不 evict（源码级）：含图 tool_result 被 applyToolResultBudget 原样透传（hasImageBlock → return 整块，注释 "sent as-is to Claude"）；时间触发清理默认关；cached-MC ant-only 且只认 8 个内置工具、不碰我们的 MCP observe()。所以 SDK 和 mini(iw=0) 都在全量累积同样的图、每轮重发 —— 等长的一集，两者请求应当一样大。
  • 字节 vs token：图字节重、token 轻（1.1MB ≈ ~1.5k token）。32MB 字节墙在 ~29 帧就撞上，而 167k token 的 auto-compact 要 ~100 帧才到 —— 图密集时先撞字节墙，proactive 的 167k 压缩救不了你，真正兜底的是撞墙后的 reactive-compact / 报错让用户 /compact。

那 <10MB vs >32MB 的观测怎么解释？不是逐帧淘汰、也不是图大小，而是兜底 + 集长：mini iw=0 没兜底、单调涨到撞 32MB；SDK 有 compaction 兜底被 reset，且我们当时监控的 SDK 集很可能累积的帧还没多到接近上限。要坐实，真数一个 late SDK 请求里有几张图即可（见 §7）。

5. 真正的 confound：不是「窗口大小」，是「兜底」

订正后：同一个 VLN 任务,image_window=0 的 mini 和 SDK 给模型的视觉历史其实一样多（都全量累积同样大小的图）—— 不是「视觉记忆量不等」。真正不等的是兜底行为:
  • mini(iw=0):无兜底 → 单调膨胀 → Anthropic cell 撞 32MB。
  • SDK:有 compaction 兜底(167k auto / 媒体超限 reactive)→ 到点整段压缩重置。
所以对比时:要么给 mini 也上兜底(image_window=K 或 compact_at),要么两条都用 Files API,并把「有没有兜底、阈值多少」记进 harness_inherent —— 这才是真正该记的 confound（不是「窗口大小」）。

另一个精确点:32MB 是 Anthropic API 专属限制,只咬 mini 的 Anthropic cell(sonnet/opus);本地 qwen 走 ollama,撞的是 served_context(128k)不是 32MB。

7. 已落地 + 待验证

已落地:每条 adapter 的 inherent 加了 vision_context 字段(harnesses/claude_sdk.py · mini_swe.py · codex_cli.py),每份 summary.json 的 harness_inherent 都会带上它。

待验证(一步就能坐实订正):在监控到的某个 late-episode SDK 请求里数 image block ——

  1. 若很多张(≈全历史) → 印证「不 evict、全量累积」(订正后的预期);
  2. 若很少 + 出现一条 "continued from previous conversation" 摘要消息 → 说明中途触发了 full-compact —— 那才是 SDK 请求变小的真因,不是近窗淘汰。
