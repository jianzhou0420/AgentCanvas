Harness 隐性差异：vision 上下文管理（以及为什么它污染对比）

这页记录 harness 之间那些不写在 cell 名里、却会影响「哪个 harness 强」结论的隐性差异。第一条（也是发现的起点）：三条 harness 对视觉历史的处理策略根本不同 —— SDK/CC 自动只保留近窗几帧，mini 默认全带，这让模型拿到的「视觉记忆量」不等，是对比里的一个真实 confound。

一句话：Anthropic API 默认每轮重发全部历史图片字节（官方明说），单请求上限 32MB，超了 413。mini 忠实照做（image_window=0 全带 → 线性膨胀 → Anthropic cell 会撞 32MB）；而 Claude Code / Agent SDK 只把最近几帧 tool_result 图发上去（旧的 observe() 帧被丢弃），所以图像密集的一集请求也稳在个位数 MB。这个行为官方没文档化，但用你的数据能反推出来。已在 harness_inherent.vision_context 里把每条 harness 的策略记下来。

1. 为什么单开这一页

我们的 summary.json 已经记 harness_inherent（auth / thinking / turn_cap）—— 因为这些是「不在 cell 名里、但决定结果」的 harness 固有事实。vision 上下文管理是同一类:两条 harness 给模型的视觉历史不等量,直接影响导航成败,却一直没被记下来。这页 + 新增的 vision_context 字段补上它。

2. 事实层：API 怎么处理图

  • 单请求上限 32MB（标准端点;Bedrock/Vertex 更低),超出返回 413 request_too_large;单图 10MB base64;一次 >20 张图触发更严的尺寸限制。
  • 默认每轮重发全历史。官方 Vision 文档原话:"each request resends the full conversation history. If images are base64-encoded, the full image bytes are included in the payload on every turn." —— API 本身不做任何 vision 裁剪。
  • 交互式 Claude Code 不自动删「用户贴的图」（issue #52224,feature request,已关;只有 /compact、/clear、开新 session）。

注意 #52224 说的是用户贴的图;我们的 observe() 图是经 MCP 回来的 tool_result 图 —— 这一类由 agent loop 管理,行为不同(见 §4)。

3. 三条 harness 的 vision 策略

harness视觉历史策略harness_inherent.vision_context
sdk(Claude Code / Agent SDK)只保留近窗几帧 tool_result 图,旧帧自动丢(未文档化,实测有界)recent-window auto (…~single-digit MB)
mini(mini-swe / ReAct)image_window=K 保留最新 K 帧,旧的塌成 text stub;默认 0 = 全带(当前 cell 默认)→ 线性膨胀image_window=K newest frames (default 0 = full history)
codex(Codex CLI)codex 自管,未审计codex-managed (unaudited)

mini 的 image_window 在 beta-react-harness/model.py,注释自称「the one declared deviation from mini's 'no context management'」。当前 std cells 跑 image_window=0(cells.py 确认)。

4. 数据反推：CC 确实在窗口化

量一帧 wp 全景:1536×411,822KB PNG ≈ 1.1MB base64。一集 ~60 次 observe,若像 mini 那样全带:

full history  ≈ 60 帧 × 1.1MB  ≈ 66MB   ← 远超 32MB,mini(image_window=0)在此崩
CC 实测       < 10MB                     ← 只可能装下 ~5–8 张近帧

60 帧全带会到 ~66MB,而监控到 CC 一直 <10MB → 它没发全历史,只留了近窗几帧。这是铁证。机制未文档化(翻遍 Claude Code / Agent SDK docs、changelog 都没有),但行为确凿,且和「>20 图触发严限」一致 —— 留少量近图才能既合法又小。(次要可能:CC 也可能对图降采样,但 60 图本身就会撞 >20-图 严限,所以「丢数量」是主因。)

5. 这是对比的 confound —— 怎么对齐

同一个 VLN 任务,image_window=0 的 mini 把整段视觉历史喂给模型,CC 只喂近窗几帧。视觉记忆量不同 → 导航能力不可直接比。做「哪个 harness 强」时,要么:
  • 把 mini 的 image_window 设成和 CC 等效的 K(需先测 CC 的窗口大小,见 §7),或
  • 两条都改用 Files API 统一图策略,或
  • 至少把差异记进 harness_inherent.vision_context(已做)+ 报告里点明,别当同一件事比。

另一个精确点:32MB 是 Anthropic API 专属限制,只咬 mini 的 Anthropic cell(sonnet/opus);本地 qwen 走 ollama,撞的是 served_context(128k)不是 32MB。

6. 想要「有保证」的图管理(别依赖未文档行为)

杠杆做法状态
Files API(file_id)图上传一次、按 id 引用,请求恒小(与图数量无关)官方文档化推荐
Context editing clear_tool_uses_20250919服务端清旧 tool_result(换占位符)文档化 beta 原语,和 CC 内部做法平行

7. 已落地 + 待验证

已落地:每条 adapter 的 inherent 加了 vision_context 字段(harnesses/claude_sdk.py · mini_swe.py · codex_cli.py),每份 summary.json 的 harness_inherent 都会带上它。

待验证(一步就能确认机制):在监控到的某个 late-episode 请求里看两件事 ——

  1. 有几个 image block(预期近窗几张,不是全部 → 确认窗口化 + 量出 K);
  2. 是 base64 还是 file_id(区分「近窗裁剪」vs「Files API 自动上传」—— 两者都解释小请求,但对齐做法不同)。
