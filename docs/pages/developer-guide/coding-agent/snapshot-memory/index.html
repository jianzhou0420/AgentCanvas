Snapshot 记忆：位姿锚定的 2D 关键帧记忆（而非 3D 重建）

一个 household / 具身 agent 的记忆形式:与其把环境重建成 3D(点云/voxel/TSDF/高斯/NeRF)——VLM 又吃不了 3D、也没有足够 3D 数据去训一个 3D-native VLM——不如在运行中持续拍照并给每帧打上相机位姿,再从上千帧里选出七八张有代表性的关键帧作为这间屋子的记忆。单次 reasoning 只把这几张位姿锚定的快照塞进 API。本文把这个 idea 精确重构、评估可行性、定位到 prior art,并给出可在现有 habitat 上直接起步的方法论与分阶段计划。

一句话：这不是 3D 重建,是「位姿锚定的 2D 关键帧记忆」(posed keyframe / view-graph) —— 3D 只是每张图的位姿元数据,不建任何 3D 模型。这恰恰是优点:VLM 原生吃 2D、绕开 3D 数据荒;而位姿又补上了纯图袋子缺的空间结构。它同时直接解掉 harness-notes 里的请求膨胀(只发 7-8 张,不是 1000 张也不是滑窗),给 真机 一个记忆底座,并有硬核的生物学依据(昆虫/鸽子的 snapshot 归巢)。可行,且能在我们现有轨迹上先离线验证。

1. 先把 idea 说准：不是重建，是「带位姿的快照集」

你说的「2D 的 3D 重建」,技术上更准确的名字是 posed keyframe set / view-graph:一组 (图像, 6-DoF 位姿, 语义标签) 三元组,外加轨迹给出的邻接边。没有 dense 3D、没有 mesh、没有辐射场。价值恰恰在「不重建」:

  • VLM 原生:记忆单元就是图片,直接进 API,不需要 3D-native VLM,也绕开「没有足够 3D 数据」这个死结 —— 这正是你的核心论点。
  • 位姿补上空间结构:纯图片袋子不知道「哪张在哪」;加了位姿,就能做「离我最近的记忆」「沿路径的记忆」「我现在在哪」——拿到 2.5D 的空间推理,却不付 3D 的表示/训练代价。
  • 压缩即记忆:1000 帧 → 7-8 张,单次 reasoning 只打包这几张。

2. 为什么可行 + 为什么现在做（咬合三处）

咬合点关系
harness-notes（请求膨胀）全带 1000 帧撞 32MB;滑窗只保留「最近」而非「最有信息」。Snapshot 记忆选「最有代表性的 K 张」,配 Files API(file_id 引用)请求恒小 —— 是那个问题的正解。
real-robot（位姿来源）Unitree 里程计 / VIO 给位姿;habitat 直接给 GT 位姿。位姿是这套记忆的前提,而我们两边都有。
reasoning（工作记忆）把「进单次调用的那几张图」当成 agent 的显式工作记忆,可读、可控 —— 和「让推理可见」一脉。

3. 生物 / 认知依据（你的直觉是对的）

你说「人回忆的不是 3D 空间,而是一张张模糊的 2D 图片;找手机时脑子飞速扫过各房间的印象;睁眼一看和记忆中的差不多,就知道自己在客厅桌子旁」—— 这在导航神经科学里是成熟理论,叫 view-based / snapshot 归巢:

昆虫(蜜蜂、蚂蚁、黄蜂)靠把当前视图和存下的 egocentric 快照做匹配来回到熟悉地点(Cartwright & Collett 1983 的 snapshot 模型)。现代版本用低分辨率全景视图 + 边缘等初级特征,甚至逐像素强度差的相似度梯度就够归巢;鸽子也用 snapshot 式的全景记忆做空间重定向。

所以你的「睁眼对一下记忆快照 → 判断我在哪」不是比喻,而是可以直接实现的自定位原语(见 §5 的 localization 组件)。

4. Prior art 定位（诚实：组件都有，我们的角度在哪）

方向代表给了我们什么 / 差在哪
长视频 VLM 关键帧选择AdaRD-Key、Event-Anchored FS、KTV选择算法(relevance+diversity+coverage);但把视频当被动流,无位姿、无主动探索、无自定位
具身情节记忆 + 检索ReMEmbR(NVIDIA)、OpenEQA、Mind Palace位姿 + captioned 帧存向量库、LLM 迭代检索;但记忆是 caption(文字),已知「caption 噪声大、视角不一致,被当 oracle」—— 我们改喂原图规避
VLN 拓扑 / 图记忆DyNaVLM、MapNav、GIST、cognitive memory graphkeyframe 作 visual anchor、图记忆引导 VLM —— 和本 idea 最近;多为在线导航决策,较少把「塞进单次小请求 + snapshot 自定位」当一等公民
view-based 归巢(生物/机器人)snapshot 模型、image-matching homing自定位/归巢的原理来源
我们的角度（值得做的差异化）：(1) 记忆是原始位姿快照、直接进每一次小 reasoning 调用作工作记忆(不是 caption 检索库,规避 caption 噪声);(2) 选择预算 K 由「一次请求装得下多少」驱动 —— 把它当成harness 级记忆管理底座,不只是精度技巧;(3) 把 snapshot 自定位闭环(当前视图→最近关键帧→「我在哪」)接进 VLM agent loop;(4) 主动、在线、带位姿;(5) 完全不做重建。这套组合,而非任一单点,是贡献。

5. 方法论：四个组件

5.1 采集 —— pose-tagged frames

agent 每走一步就 observe() 拿一帧,附上相机 6-DoF 位姿。位姿来源:habitat 直接给 GT;真机用 Unitree 里程计 / VIO(有漂移,见 §8)。每帧 = (image, pose, t)。

5.2 关键帧选择 —— 「七八张」这一步的核心

两段式:在线插入 + 离线压缩到预算 K,三准则 覆盖 / 多样 / 相关:

# 在线（SLAM-keyframe 式）：满足任一即插入新关键帧
insert if  Δpose > τ_pos  or  Δheading > τ_ang        # 几何覆盖
        or  embed_dist(frame, last_kf) > τ_vis        # 视觉新颖度(DINO/CLIP 特征)
        or  new_objects_detected(frame) not in memory  # 语义新增(开放词检测)

# 离线压缩到预算 K（一次装得下的张数，如 8）
1) 语义 set-cover：选最小帧集，覆盖所有检测到的语义实体
2) farthest-point：在 pose ⊕ embedding 联合空间里做最远点采样，补足多样性/覆盖
3) 相关性重排：若已知任务/查询，按 query-relevance 提权（可选）

语义 set-cover 是关键:把「覆盖一屋的信息」形式化成「最小帧集覆盖所有物体/地标」。「7-8 张」是这个覆盖问题在典型卧室上的经验解 —— 是否成立是可测的经验问题(Phase 0 直接量)。

5.3 记忆存储 —— view-graph

node = {image(或 file_id), pose, caption/tags, embedding};edge = 轨迹邻接 / 可达。这就是一张「视图图」:既能按空间近邻查,也能沿路径走。

5.4 检索 → 单次 reasoning

推理前,从 view-graph 取最相关的 K 张塞进这一次 VLM 调用:

  1. 任务相关:query↔image(CLIP 文图 / caption 匹配)——「去厨房」→ 含厨房的快照。
  2. 空间相关:离当前位姿近 / 沿目标路径的关键帧。
  3. 自定位(snapshot homing):当前帧 embedding ↔ 关键帧库最近邻 →「我在客厅桌子旁,朝厨房」。这就是你说的「睁眼对一下记忆」。

把 top-K(7-8)位姿快照 + 每张的 pose/caption 标注 + 当前视图 + 任务 一起喂 VLM。请求小、可读、空间有据。

6. 落到我们系统

一个 memory bridge / tool,和现有 MCP bridge 同形:

@mcp.tool()
def observe():        # 照旧回当前帧；bridge 顺手记 (image, pose) 进 view-graph
    ...
@mcp.tool()
def recall(query):    # 返回 top-K 位姿快照（file_id 引用，请求恒小）
    kfs = view_graph.retrieve(query, cur_pose, cur_frame, k=8)
    return [image_block(kf) for kf in kfs]            # 直接进下一次 reasoning
@mcp.tool()
def where_am_i():     # snapshot 自定位：当前帧 → 最近关键帧
    return view_graph.localize(cur_frame)             # "客厅桌旁，朝厨房"

关键帧走 Files API(上传一次、file_id 引用),直接吃掉 harness-notes 的请求膨胀。检索既可由 agent 主动调 recall()(ReAct 友好),也可 harness 自动注入。

7. 评测 + 基线（现有 habitat 就能起）

我们已有 R2R-CE 轨迹,带 frames + GT 位姿,离线就能验证核心假设。

指标问的问题
紧凑度 K覆盖一个场景要几张?「7-8」在真实轨迹上成立吗?
覆盖率选出的 K 张覆盖了多少比例的语义实体 / 可行走空间?
下游 VLN(SR/SPL/nDTW)只给 keyframes,导航掉多少?对比全历史?
请求大小vs 全历史 / 滑窗,单请求省多少?
自定位准确率最近关键帧 → 对不对得上真实位置?混叠多严重?

基线:全历史(mini image_window=0)/ 近窗(CC 行为)/ 均匀抽样 K / 本方法(位姿关键帧)—— 在相同请求预算下比,才公平(见 harness-notes 的 confound)。

8. 诚实的难点

  • 选择质量(主风险):「7-8 张覆盖一屋」对粗语义可能成立,对任务细节偏乐观;欠覆盖 → agent 漏东西。对策:预算自适应、任务感知选择;Phase 0 先量清楚覆盖-K 曲线。
  • 位姿漂移:真机里程计/VIO 长程漂移;habitat 无此问题。对策:先在 sim 验证方法,再谈真机回环校正。
  • 感知混叠:两个角落长得像 → 自定位歧义。对策:位姿 + 视图联合判定,而非纯图匹配。
  • 动态场景:手机被挪走 → 记忆过期。对策:时间戳 + 失效/更新机制(见到冲突就重写该节点)。
  • caption 噪声:ReMEmbR 已踩过(caption 当 oracle 出错)。对策:记忆喂原图,caption 只做检索索引不做事实来源。
  • 覆盖率如何度量:需要 GT 语义(habitat 有实例分割)才能算「覆盖了多少」——这也是先在 sim 做的理由。

9. 分阶段路线

Phase 0 · 离线分析(零新硬件,现有轨迹):在已有 R2R-CE 轨迹上实现关键帧选择,画覆盖率 vs K 曲线,可视化「几张覆盖一屋」;再跑「只用 keyframes」的下游 VLN / EQA,量掉点。—— 这一步就能证伪或证实核心假设。
Phase 1 · 接入 agent loop:memory bridge(observe/recall/where_am_i)+ Files API,在相同请求预算下做「全历史 / 近窗 / 位姿关键帧」的受控对比。
Phase 2 · snapshot 自定位:把「当前视图→最近关键帧→我在哪」做成原语,评混叠与准确率;支持「找手机」式 EQA。
Phase 3 · 真机:Unitree 里程计给位姿(接 real-robot 那条 bridge),验证漂移下的鲁棒性。
