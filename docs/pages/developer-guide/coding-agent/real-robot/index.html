把 Unitree 机器人接到 Claude Code：真机具身操作的可行性与架构

问题：能不能把 Unitree 的 Go2 / G1 / H1 接到 Claude Code，做真机具身操作探索？结论：能 —— 而且我们现在跑 VLN 的那套架构几乎直接迁移。这篇讲清楚「为什么几乎白送」「Unitree 侧到底提供什么接口」「怎么落地一个真机 MCP bridge」「已有先例」「从 CAN 动作空间研究迁移过来的直接结论」，以及诚实的安全/现实约束和分阶段路线。

一句话：我们的栈是 Claude Agent SDK → MCP stdio bridge → env(HTTP)；真机版只换最后一层 —— 把 habitat env 换成 Unitree SDK（SportClient/LocoClient/VideoClient）。claude_sdk.py 的 observe→step ReAct 环、EventSink 的 episode_*.jsonl 记录、甚至 wp 的叙述 prompt 全部复用。公开先例已存在（Go2 MCP server、go2w agent SDK、AgentRob）。三条真正的工程门槛：机型（只有 EDU 有本地 SDK）、动作抽象层级（暴露高层 Move/waypoint，别暴露关节 —— 这正是我们「抽象层级决定具身」的直接推论）、安全（Go2 可控，G1/H1 必须吊架）。

1. 可行性判定 + 三机对照

机器人形态本地 SDK（Claude 直控）高层控制感知真机安全
Go2四足✓ EDU（AIR/PRO 走 WebRTC）SportClient：Move(vx,vy,vyaw)+丰富 sport 动作前置相机（VideoClient）+可选 LiDAR较可控（小四足）
G1人形✓（开发/EDU 版）LocoClient：Move+手臂 API；FSMDev kit 深度相机（自配）需吊架（双足、会摔）
H1人形✓（同 unitree_sdk2）LocoClient 家族自配需吊架（更大更重）

「本地 SDK」＝能用 unitree_sdk2_python 经 CycloneDDS 直接下发控制。Go2 的 EDU 原生支持；AIR/PRO 面向 app/遥控，需刷固件或改走 WebRTC（go2-webrtc / unitree_webrtc_connect）。

推荐路径：Go2 EDU 先行。它是唯一一台「本地 SDK 原生 + 高层动作齐全 + 相机现成 + 相对安全」都占的机器人，和我们已有的 R2R 导航任务形态最接近。人形（G1/H1）作为第二阶段，且必须先解决吊架。

2. 为什么几乎是直接迁移

我们现在的 SDK harness 早就是「Agent 经 MCP 工具操作一个环境」的结构。把两层画出来，真机版只有最右一格变：

habitat 版（现在）:
  Claude Agent SDK ──stdio──▶ mcp_bridge.py ──HTTP──▶ env_habitat auto_host
   (claude_sdk.py)            observe()/step()          (Isaac/habitat 仿真)

真机版（本文）:
  Claude Agent SDK ──stdio──▶ unitree_bridge.py ──DDS──▶ Unitree 机器人
   (claude_sdk.py, 原样)      observe()/move()/stop()    (SportClient/VideoClient)
                                     ▲
                        唯一要重写的就是这一个文件

可以原样复用的：

  • harnesses/claude_sdk.py —— adapter 逻辑（thinking 配置、bridge 握手、事件 emit）与环境无关。
  • driver.py 的 EventSink —— episode_*.jsonl 的事件词汇（thinking/tool_use/tool_result）真机照样成立，逐集 trajectory 记录白送。
  • observe → 决策 → step 的 ReAct 环 —— 工具语义（观察拿图、动作驱动、STOP 结束）真机同构。
  • wp 的「reason out loud as visible text」叙述 prompt（prompts.py:96–100）—— 真机上你更想看每一步为什么这么走（见思维链可见性）。
  • Monitor 前端 —— 事件格式不变，直接可视化真机轨迹。

唯一要新写的：一个 unitree_bridge.py，把 mcp_bridge.py 里「HTTP 调 env」的部分换成「DDS 调 Unitree SDK」。它和现有的 wp_bridge.py 同形（都是 stdio MCP server + 一组工具）。

3. Unitree 侧：控制与感知接口

3.1 控制抽象层级 —— 这一层直接对应我们的核心结论

Unitree 的控制分两层，正好对应我们「抽象层级决定具身」里的 step 空间 vs waypoint 空间：

层级接口给 LLM？
高层（sport/loco 服务）SportClient/LocoClient：Move(vx,vy,vyaw) 速度命令 + 语义动作（StandUp/Damp/坐下/姿态…）；机身自己维持平衡✓ 就该给这个
低层（关节）逐电机 MotorCmd（力矩/位置），跑 RL/MPC 策略用✗ 别给 LLM（危险、且是模型最不擅长的层）
我们 4B 模型在低层 step 动作上近乎废掉，换到高层 waypoint 立刻能用。真机同理：给 LLM 高层速度/航点命令，让机身控制器兜底平衡与步态 —— 这不是妥协，是把模型接在对的抽象层上。

3.2 Go2（四足，首选）

from unitree_sdk2py.core.channel import ChannelFactoryInitialize
from unitree_sdk2py.go2.sport.sport_client import SportClient

ChannelFactoryInitialize(0, "eth0")          # 有线接机器人，指定网卡
sport = SportClient(); sport.Init()
sport.Move(0.3, 0.0, 0.0)                     # 前进 0.3 m/s
sport.StopMove()                              # 停
# 相机：VideoClient.GetImageSample() 取前置相机一帧（RPC）
  • 控制：SportClient（sport mode），高层 Move + 大量语义动作，方法与 unitree_sdk2 C++ 一致（见 Sports Services）。
  • 感知：前置相机经 VideoClient（RPC 取帧）；部分机型带 LiDAR（L1）出点云 —— 可给 observe() 附一个 clearance 读数，和 habitat 的 observe() 一模一样。
  • 连接：EDU 原生 CycloneDDS；AIR/PRO 走 WebRTC（go2-webrtc、unitree_webrtc_connect、go2_ros2_sdk）。

3.3 G1 / H1（人形，第二阶段）

from unitree_sdk2py.g1.loco.g1_loco_client import LocoClient
ChannelFactoryInitialize(0, "eth0")
loco = LocoClient(); loco.Init()
loco.Damp(); loco.StandUp(); loco.Start()     # FSM：阻尼→站起→进入行走
loco.Move(0.3, 0.0, 0.0); loco.StopMove()
  • 控制：LocoClient 高层，同样是 Move(vx,vy,yaw) + 语义动作；但有状态机（必须 Damp → StandUp → Start 才能走），bridge 要显式管理。（社区反馈：某些版本 Move() 需在内部先 Start() 才动 —— 落地时按实机 firmware 校准。）
  • 感知：不像 Go2 有现成前相机服务，通常自配深度相机（RealSense/Livox），感知这层要自己搭。
  • H1：同 unitree_sdk2 的 loco 家族，更大更重。
  • 生态：LeRobot 已支持 G1（模仿学习/遥操作数据），可作为感知/数据侧参考。

4. 落地：真机 MCP bridge 骨架

把工具语义从 habitat 映射到真机 —— 一一对应，语义几乎不变：

habitat 工具真机等价（Go2 / G1）
observe() → RGB(+clearance)VideoClient.GetImageSample()（Go2 前相机）/ dev-kit 深度相机；LiDAR 出 clearance
step([1,2,3,0]) 离散动作累计成一段 Move(vx,vy,vyaw) 速度命令并保持 Δt；0=STOP → StopMove()+Damp()
goto(waypoint)（wp）朝候选航点 Move 直到到达 / 接 Unitree 内置导航 / 自建 waypoint 预测
look_around() 四视原地 Move(0,0,yaw) 旋转采多帧拼全景
stop()StopMove() + Damp()

bridge 骨架（和 wp_bridge.py 同形，MCP stdio server + 工具）：

from mcp.server.fastmcp import FastMCP
from unitree_sdk2py.core.channel import ChannelFactoryInitialize
from unitree_sdk2py.go2.sport.sport_client import SportClient
from unitree_sdk2py.go2.video.video_client import VideoClient

ChannelFactoryInitialize(0, "eth0")
sport = SportClient(); sport.Init()
video = VideoClient(); video.Init()
mcp = FastMCP("unitree")

@mcp.tool()
def observe() -> list:                        # 回一帧图（base64），像 habitat 的 observe()
    ok, jpeg = video.GetImageSample()
    return [image_block(jpeg)]                # 走和 look_around 一样的图像回传

@mcp.tool()
def move(vx: float, vy: float, vyaw: float, seconds: float) -> str:
    guard(vx, vy, vyaw)                       # ← 关键：夹住速度上限，见 §6 安全
    t0 = time.monotonic()
    while time.monotonic() - t0 < seconds:
        sport.Move(vx, vy, vyaw); time.sleep(0.02)
    sport.StopMove()
    return "moved"

@mcp.tool()
def stop() -> str:
    sport.StopMove(); sport.Damp(); return "stopped (episode ended)"

mcp.run()                                      # claude_sdk.py 用它替掉 mcp_bridge.py

真机版和 habitat 版走同一个 claude_sdk.py：只是 ClaudeAgentOptions.mcp_servers 指向 unitree_bridge.py 而非 mcp_bridge.py。感知回路、事件记录、ReAct prompt 全不动。

5. 已有先例（可行性已被证明，以及我们强在哪）

项目做法局限（我们能补）
lpigeon/unitree-go2-mcp-serverMCP server：自然语言 → ROS2 命令，接 Claude Desktop命令式、无感知回路（不回图），NL 一次性指令，非紧密 observe→act 环
grasp-lyrl/unitree_go2w_agent_sdk面向 AI agent 的统一「感知+规划+控制」API非我们的轨迹/消融基建
AgentRob（arXiv 2602.13591）LLM agent 层 + MCP 工具 + VLM 控制器，Go2 作执行体偏系统/安全叙事
我们比现成 MCP server 强的三点：(1) 已有图像反馈的 observe→act 环（现成 server 大多命令式无回图）；(2) 已有逐集 trajectory 记录 + Monitor 可视化；(3) 已有动作空间消融基建（step vs waypoint 的 2×2），可以直接把「哪种真机动作抽象对 LLM 最友好」做成受控实验。换句话说：别用现成 NL server，把真机接进我们自己的 harness。

6. 安全与现实约束（诚实一节）

  • 速度/动作夹取（硬性）：bridge 里 guard() 必须夹住 vx/vy/vyaw 上限、单次时长、以及禁用危险 sport 动作（跳跃/翻滚）。LLM 是不可信控制源 —— 参考 Jailbreaking LLM-Controlled Robots（arXiv 2410.13691）。
  • 物理 E-stop + 遥控器随手：真机必须有人拿遥控器兜底，随时抢占。
  • Go2：小四足，空旷场地 + 系绳即可，相对可控。
  • G1/H1：双足会摔、重、贵 —— 真机行走实验必须吊架/harness/龙门。第一阶段不要碰人形。
  • 不可复现：真机没有 habitat 的 seed，同一指令每次不同；评测要改成多次重复 + 人工标注，而非 R2R 的确定性回放。
  • 延迟：LLM 决策是秒级、实时平衡是毫秒级 —— 正因为给的是高层命令，机身控制器在两次 LLM 调用之间自己维持稳定，这个 gap 才被吸收（又一次印证「接在高层」）。
  • sim2real：先在仿真里把 bridge 跑通再上真机。

7. 分阶段路线（推荐）

Phase 0 · 零硬件：在 Unitree MuJoCo / Isaac 仿真里跑同一个 unitree_bridge.py，验证 observe→move→stop 环和事件记录。零风险、可复现。怎么选平台、两种 bridge 后端怎么接，见 §8。
Phase 1 · Go2 EDU 真机：高层 SportClient + VideoClient，复用 R2R 式导航任务（「走到厨房角落停下」），系绳 + 遥控兜底。产出：真机版 episode_*.jsonl，Monitor 直接可视。
Phase 2 · 真机 waypoint：把 wp 动作空间搬上真机 —— 用 Go2 LiDAR/深度预测候选航点（正好对上我们已有的 waypoint 预测 shim），做「真机上 step vs waypoint」的受控对比。
Phase 3 · G1 人形（吊架）：LocoClient + FSM 管理，感知自配深度相机。仅在龙门/harness 下。

8. 在仿真里先跑：MuJoCo / Isaac Sim / Isaac Lab

上真机前先在仿真里把 bridge + observe→act 环跑通,是 Phase 0。好消息:三条路都能跑,而且 Unitree 官方 MuJoCo 让「同一个 bridge 仿真真机通用」变成字面意义 —— 改个网卡名而已。按需求选:

仿真同 DDS/SDK 接口?感知保真最适合
unitree_mujoco(官方)✓ 完全相同(lo vs 真机网卡)基础(需自加 MuJoCo 相机)验证控制环 + DDS 接口 + sim↔real 零改
Isaac Sim(go2_omniverse / isaac-go2-ros2)ROS2 接口(非 DDS 直连)高:RTX 光追 RGB+depth+语义分割VLM 视觉导航 + snapshot-memory 覆盖度量(语义分割当 GT)
Isaac Lab(unitree_rl_lab / unitree_sim_isaaclab)G1/H1 有 DDS 版;RL 训练高训/验低层 locomotion 策略、大规模并行、人形

8.1 MuJoCo —— 同一个 bridge，仿真真机零改

Unitree 官方 unitree_mujoco 基于 unitree_sdk2 + MuJoCo,用和真机完全相同的 DDS 接口。unitree_sdk2_python(SportClient/LocoClient)的控制程序,只改网卡名就在 sim / 真机之间切换:

ChannelFactoryInitialize(0, "lo")     # 仿真：loopback
# ChannelFactoryInitialize(0, "eth0") # 真机：改成真机网卡，其它一字不改
sport = SportClient(); sport.Init(); sport.Move(0.3, 0.0, 0.0)

所以我们的 unitree_bridge.py(§4)在 MuJoCo 里零改动运行。代价:MuJoCo 渲染基础,官方 sim 偏控制/本体,相机要自己加(MuJoCo 有相机渲染,但 VideoClient 那套 RPC 相机不一定被 sim 服务)—— 所以 MuJoCo 用来验「控制环 + DDS 接口」最稳,VLM 视觉落地交给 Isaac Sim。(注意:sim 的 DDS domain id 要和真机区分,免得串台。)

8.2 Isaac Sim —— 光追相机，VLM 视觉最佳

社区已有现成 Go2/G1 Isaac Sim 工程(go2_omniverse、isaac-go2-ros2、Go2_Isaac_ros2)。Go2 在 Isaac Sim 里经 ROS2 topic 发 RGB + 深度 + 语义分割(如 /unitree_go2_0/front_cam/color_image),RTX 光追 → 照片级。这对 VLN 视觉落地最重要,而且语义分割可直接当 snapshot-memory 覆盖率的 GT。

接法:bridge 后端换成 ROS2,MCP 工具面(observe/move/stop)一字不变:

@mcp.tool()
def observe():        # 订阅相机 topic 取一帧（+可选 depth 当 clearance）
    return [image_block(latest_ros2_frame("/unitree_go2_0/front_cam/color_image"))]
@mcp.tool()
def move(vx, vy, vyaw, seconds):   # 发布 /cmd_vel (Twist) 或 go2_omniverse 的速度接口
    publish_cmd_vel(vx, vy, vyaw, seconds)

ROS2 后端也能上真机(经 unitree_ros2),所以「DDS 后端(MuJoCo/真机)」和「ROS2 后端(Isaac Sim/真机)」两套,MCP 工具面对 claude_sdk.py 完全一致 —— 换后端不换 harness。

8.3 Isaac Lab —— 要练低层策略 / 人形时才用

官方 unitree_rl_lab(IsaacLab)支持 Go2 / H1 / G1-29dof 的 velocity locomotion(G1 还有 mimic);unitree_sim_isaaclab(G1 / H1_2)也是同 DDS 接口。Isaac Lab 是大规模并行 GPU 训练框架 —— 我们做 VLM-in-loop 导航用不到它训策略,除非要自己练/验低层步态或上人形高保真。

推荐:控制环 + 接口验证 → MuJoCo(零改、最稳);VLM 视觉导航保真(我们真正要的) → Isaac Sim(ROS2 光追相机 + 语义分割);要练低层步态或人形 → Isaac Lab。和 habitat 的关系:互补不替代 —— habitat 给 VLN 场景+指令(无机器人本体),Isaac/MuJoCo 给机器人本体 + 真实控制接口 +(Isaac)光追相机。
坑:Isaac Sim/Lab 吃 NVIDIA GPU + 安装较重(Omniverse);MuJoCo 轻但相机弱、需自配;两者都要把 sim 的 DDS/ROS2 命名空间和真机区分开。

9. 需要你定的决策点

  • 有没有实机 / 哪台？（有 Go2 EDU → 直接 Phase 1；只有 AIR/PRO → 走 WebRTC 或先 Phase 0 仿真；有 G1/H1 → 先备吊架）
  • sim-first 还是直接真机？先用哪个仿真？（建议先 Phase 0；控制/接口验证走 MuJoCo〔同 DDS、bridge 零改〕，VLM 视觉导航走 Isaac Sim〔光追相机 + 语义分割〕—— 见 §8）
  • 连接方式：DDS（EDU，官方 unitree_sdk2_python）还是 WebRTC（AIR/PRO，社区驱动）
  • 任务形态：沿用 R2R 导航指令，还是新定探索/操作任务
