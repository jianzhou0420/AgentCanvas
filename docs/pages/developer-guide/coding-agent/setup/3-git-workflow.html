Git 工作流：worktree、分支、与上游同步（中文）

Claude Code worktree 的工作原理、分支怎么开怎么合并回去、每天怎么跟上快速更新的上游（以 ../SWE-agent 为例）、以及自己的文件怎么不被 pull 冲掉。

本页回答四个具体问题：① Claude Code 里的 worktree 到底是什么、改动怎么回到主目录（§2）；② branch 是什么、开出去之后怎么合并回去（§3）；③ 像 SWE-agent 这种上游一天好几个提交的仓库，每天怎么保证拉到最新版（§4）；④ 我在别人的仓库里加了自己的文件，拉新时怎么保证它们不被删（§5）。§1 先花三分钟建立心智模型——后面所有命令都靠这张图理解，不用死记。系列前篇：CAN 项目计划。

1. 三分钟心智模型：仓库、提交、分支、工作区

一个 git 仓库物理上就是两样东西：

  • .git/ 数据库——存全部历史。每次 git commit 存一个完整快照，快照之间用「父指针」串成链。提交进了这个库就几乎删不掉（哪怕操作失误也能用 git reflog 找回来）。
  • 工作区（working tree）——你实际看到、编辑的那份文件。它只是数据库里某个快照「摊开」的样子。

分支（branch）不是文件夹的副本，只是一个指针——一张写着提交编号的便签。main 是一张便签，你开的 can-dev 是另一张。在哪个分支上提交，哪张便签就往前挪一格。HEAD 表示「你现在站在哪张便签上」。

A --- B --- C --- D   ← main（上游的历史）
             \
              E --- F   ← can-dev（你的提交）
                    ↑
                   HEAD（你现在在这）

所以「开分支」瞬间完成、不占空间；「合并」「rebase」这些词全都只是挪便签、接链条的不同方式。带着这张图往下看。

2. Claude Code 的 worktree 是怎么工作的

2.1 git 原生功能：一个数据库，多个工作区

git worktree 是 git 自带的功能（不是 Claude Code 发明的）：让同一个 .git/ 数据库同时摊开成多个工作目录，每个目录检出（checkout）不同的分支：

AgentCanvas/            ← 主工作区，检出 dev/coding-agent
AgentCanvas-fix/        ← worktree 1，检出 fix-bug 分支
AgentCanvas-doc/        ← worktree 2，检出 doc-update 分支
（三个目录共享同一份历史，谁 commit 了另外两个立刻能看到）
git worktree add ../AgentCanvas-fix -b fix-bug   # 建目录 + 开新分支，一步完成
git worktree list                                # 看现在有哪些工作区
git worktree remove ../AgentCanvas-fix           # 用完删掉（历史还在，只删目录）

两条规则：① 同一个分支同时只能被一个工作区检出（防止两边同时改乱掉）；② 删 worktree 用 git worktree remove，不要直接 rm -rf（残留登记信息要再 git worktree prune 清）。

2.2 Claude Code 拿它做什么

Claude Code 用 worktree 解决一个问题：几个任务并行改同一个仓库时互相踩文件。典型场景：

场景行为
并行 subagent 各自改文件（Agent 工具的 isolation: "worktree"）每个 agent 拿到一个独立 worktree + 独立分支，改完各自 commit；没改动的 worktree 自动清理
主会话想在隔离环境里做一个大改动（EnterWorktree）整个会话切进一个新 worktree 工作，主目录保持干净，随时能对比
你自己同时开两个 Claude Code 终端跑同一个仓库手动给第二个终端 git worktree add 一个目录，两边永不冲突

2.3 worktree 里的改动怎么回到主目录

worktree 不是「另一个仓库」，所以不存在「传回去」——它 commit 的瞬间，提交就已经在共享的数据库里了。要让主目录的分支拿到这些改动，就是一次普通的合并（§3 详讲）：

# 在主目录里：
git merge fix-bug                    # 把 worktree 分支的提交合进当前分支
git worktree remove ../AgentCanvas-fix
git branch -d fix-bug                # 合并完，分支便签也可以撕掉

心智模型检查 worktree = 同一份历史的多个「摊开点」。commit 是全局的，只有未提交的工作区文件是各目录私有的。所以 worktree 很轻（不复制历史），也所以「合并回去」和普通分支合并没有任何区别。

3. 分支：开出去，再合并回来

3.1 完整生命周期（五条命令）

git switch -c my-feature    # ① 开新分支并站过去（旧写法：git checkout -b）
# ...改文件...
git add -A && git commit -m "做了 X"   # ② 在分支上提交（可以很多次）
git switch main             # ③ 回到 main
git merge my-feature        # ④ 把分支的提交合进 main
git branch -d my-feature    # ⑤ 删掉便签（提交已在 main 里，删的只是名字）

3.2 merge 的两种形态：快进 vs 合并提交

第 ④ 步会遇到两种情况，git 自动选择：

情况一：你开分支后 main 没动过 → 「快进」（fast-forward）
A --- B --- E --- F          git 直接把 main 便签挪到 F，
      ↑           ↑          历史一条直线，什么都不用造。
    main(旧)   main(新)=my-feature

情况二：你开分支后 main 也前进了 → 「合并提交」（merge commit）
A --- B --- C --- D --- M    ← main（M 是自动生成的合并提交，
       \               /        两条线在这里汇合）
        E --- F ------          ← my-feature

3.3 冲突：什么时候发生，怎么处理

只有两边改了同一个文件的同一片区域才冲突。git 会停下来，把两个版本都写进文件里让你选：

<<<<<<< HEAD
main 这边的写法
=======
my-feature 那边的写法
>>>>>>> my-feature
git status                  # 看哪些文件冲突（unmerged）
# 编辑文件：留下想要的内容，删掉 <<< === >>> 三行标记
git add 冲突的文件
git commit                  # 完成合并
# 慌了想撤销整次合并：git merge --abort（回到 merge 前，无损）

rebase 一句话 你还会经常见到 git rebase：作用和 merge 一样是「把两条线的工作合到一起」，区别是它不造汇合点，而是把你的提交拔起来、挪到对方最新提交后面重放，历史保持一条直线。个人分支跟上游同步时常用它（§5.3），冲突处理方式和 merge 一样，逃生舱是 git rebase --abort。

4. 每天与上游 SWE-agent 保持同步

4.1 先弄懂 fetch 和 pull 的区别

你的 ../SWE-agent 克隆自官方仓库，git 把官方地址记作 origin。仓库里其实有两张 main 便签：

  • main——你本地的；
  • origin/main——「我上次联网时看到官方在哪」的本地缓存，不联网它永远不动。

git fetch = 联网下载新提交、更新 origin/main 这张便签，完全不碰你的文件（绝对安全，随便跑）。git pull = fetch + 顺手把 origin/main 合进你的 main。所以「怕 pull 出事」的正确做法是拆开：先 fetch 看看，再决定合不合。

4.2 每日例行（三条命令）

cd ../SWE-agent
git fetch origin                          # ① 下载上游最新（不碰工作区）
git log --oneline main..origin/main       # ② 看看上游比我新了哪些提交（可跳过）
git pull --ff-only                        # ③ 快进到最新

--ff-only 的意思是「只允许快进，否则拒绝」。只要你从不在 main 上做自己的提交，pull 就永远是 §3.2 的情况一——纯挪便签，不可能冲突、不可能出事。哪天它突然拒绝了，就是在提醒你：你在 main 上提交了自己的东西，该按 §5.3 把它们挪到自己的分支去。

纪律：main 只做上游的镜像 永远不在 main 上提交自己的改动——你的东西放自己的分支（§5.3）。守住这一条，「每天拉最新」就是一条零风险命令，可以设成别名：git config --global alias.up "pull --ff-only"，以后每天 git up 即可。

5. 自己的文件不被更新冲掉：三层方案

5.1 先安心：pull 本来就不会删你的文件

git 把你新建的、从没 git add 过的文件叫 untracked（未跟踪）。关键事实：git pull 从不删除、不覆盖 untracked 文件。唯一的边界情况是上游恰好也新增了同名文件——这时 pull 会报错停下（"would be overwritten by merge"），绝不会静默覆盖，你把自己的文件改个名再拉即可。

真正会动你文件的是这几个命令，认清它们：

命令对 untracked 文件对已跟踪文件的未提交修改
git pull / git merge不碰（同名冲突则报错停下）可能要求先提交或 stash
git reset --hard不碰丢弃
git clean -fd删除！不碰

唯一真正的危险命令是 git clean——它的本职就是「删掉所有 untracked 文件」。不确定时先跑 git clean -nd（-n = 只列出会删什么，不真删）。

5.2 方案 A（最轻）：不跟踪 + 本地 ignore

适合笔记、草稿脚本这类「只想放在这里、不需要版本管理」的文件。让它们保持 untracked，并写进本地私有的 ignore 文件，防止哪天手滑 git add -A 把它们加进去：

# .git/info/exclude 的语法和 .gitignore 一样，
# 但它只存在你机器上，不属于仓库内容，永远不会和上游冲突：
echo "my_notes/" >> .git/info/exclude
echo "scratch_*.py" >> .git/info/exclude

局限：这些文件没有历史、没有备份、换机器带不走。要认真开发，用方案 B。

5.3 方案 B（推荐）：自己的分支 + 每天 rebase

把自己的文件提交在自己的分支上，上游的历史留在 main。这是当前阶段（CAN 在 SWE-agent 上做实验）最合适的形态：

# 一次性设置：
cd ../SWE-agent
git switch -c can-dev            # 开自己的分支
git add 你的文件 && git commit -m "CAN: 实验脚本"

# 每天同步（站在 can-dev 上）：
git fetch origin                 # ① 下载上游最新
git rebase origin/main           # ② 把你的提交搬到上游最新之后重放

rebase 之后的样子（对照 §1 的图）：

rebase 前：A --- B --- C --- D   ← origin/main（上游新增了 C、D）
                  \
                   E --- F       ← can-dev（你的提交，基于旧的 B）

rebase 后：A --- B --- C --- D --- E' --- F'   ← can-dev
（你的提交被原样搬到上游最新之后；你只加了新文件的话，几乎永不冲突）

万一冲突：处理方式同 §3.3（编辑 → git add → git rebase --continue），慌了就 git rebase --abort 完整退回。

5.4 方案 C（最终形态）：GitHub fork + 双 remote

等 CAN 的改动需要发布/备份到 GitHub 时，把方案 B 升级：在 GitHub 上 fork 官方仓库，本地记两个远端——origin 指你的 fork（可推送），upstream 指官方（只拉取）：

# 一次性设置（fork 后）：
git remote rename origin upstream
git remote add origin git@github.com:billzhao1030/SWE-agent.git

# 每天同步：
git fetch upstream
git rebase upstream/main
git push --force-with-lease origin can-dev   # rebase 重写了历史，推 fork 要 force；
                                             # --force-with-lease 比 --force 安全（别人动过就拒绝）

5.5 三层方案对比

A · 不跟踪 + excludeB · 个人分支 + rebaseC · fork + 双 remote
文件有版本历史无有有
有云端备份无无有（你的 fork）
每日同步成本git up 一条fetch + rebase 两条fetch + rebase + push 三条
适合笔记、草稿本地认真开发（当前阶段）要发布、多机、写论文放代码

6. 速查表与常见坑

想做什么命令
看当前状态（永远先跑这个）git status
开新分支并切过去git switch -c 名字
把分支合回 maingit switch main && git merge 名字
每天拉上游最新（main 干净时）git fetch origin && git pull --ff-only
个人分支跟上上游git fetch origin && git rebase origin/main
merge / rebase 中途逃生git merge --abort / git rebase --abort
开一个并行工作目录git worktree add ../目录 -b 分支
删并行工作目录git worktree remove ../目录
「我好像把提交搞丢了」git reflog（HEAD 走过的每一步都在，checkout 回去即可）
坑说明 / 处理
pull 时报 "divergent branches, need to specify how to reconcile"新版 git 要求你表态。按本页纪律选快进：git config --global pull.ff only
rebase 后 push 被拒（non-fast-forward）正常——rebase 重写了历史。推自己的 fork/分支用 --force-with-lease；永远不要 force push 别人也在用的分支
手滑在 main 上做了提交，pull --ff-only 拒绝git switch -c can-dev（提交跟你走）→ git switch main → git reset --hard origin/main（把 main 退回上游）
rm -rf 删了 worktree 目录，git 还记得它git worktree prune 清掉残留登记
untracked 文件真的消失了基本只有 git clean 会干这事，而它删的文件不进 reflog、找不回来——所以重要文件尽早走方案 B 提交进历史
