wp 省图不一定省 context：每集图片数与峰值上下文统计

统计了两套 harness 上 bare 与 wp 两种动作空间的每集图片数和每集峰值上下文：qwen3.5-4b（Habitat，mini harness，全历史多轮）与 sonnet-5（VLNVerse，Claude SDK harness）。发现方向并不一致——wp 在两边都把图片数和交互轮次砍到约 1/3，但峰值 context 一边降、一边反而升。记录于 2026-07-17。

结论

wp 稳定省的是「张数」和「轮次」，不是「上下文」。图片数两边都降到 ~1/3（4b：40.8 → 12.9；sonnet：73.2 → 32.7），轮次同步降到 ~1/3。但峰值 context：4b（Habitat）wp 的中位数只有 bare 的 57%（13.7k vs 23.9k），sonnet（VLNVerse）wp 的均值反而比 bare 高 41%（43.2k vs 30.7k）。

另外注意 sonnet bare 的中位 81 张图、74.2 turns——它在 VLNVerse 上大多接近 100-turn 上限才结束，属于「跑满型」交互。

为什么方向相反

  • wp 的单张图贵得多。bare 每次 observe 是一张前向帧；wp 每次 observe 是一张 Left/Front/Right/Back 四视角拼接、带编号标注的全景条，单张 token 数远高于前向帧。张数省 2/3，单张贵数倍，净效应不定。
  • wp 条件带强制 thinking。SDK 侧 wp cell 有 thinking 预算，思考块全程留在历史里，纯文本历史比 bare 厚。
  • bare 的图小但密。4b（Habitat，512px 前向帧）单张成本低，靠张数堆 context；wp 砍掉张数后 context 中位数直接掉到 57%。
  • 哪边净胜取决于「单张成本 × 张数」与文本历史占比——两套 harness 恰好落在了分界线两侧。

口径差异，跨 harness 绝对值不可直接比。mini 侧 context = 该集最后（=最大）一次调用的 prompt_tokens（ollama 计数）；SDK 侧 = 最大一次调用的 input_tokens + cache_read + cache_creation（Anthropic 计费口径），且两边分词器不同。同一 harness 内 bare vs wp 的对比是干净的。

工程含义

  • wp 必然省的是交互轮次（≈ 时延与调用次数）；对 API 计费、在 cache 命中良好时，这是主要省钱项。
  • wp 不必然省峰值上下文（≈ 本地模型的 KV 显存、API 单次调用的账单上限）。给本地小模型配 wp 时不能按「图少所以 context 小」做容量规划——4b wp 的 max（46.9k）反而高于 bare 的 max（32.0k），长 episode 里全景条叠得更快。

统计口径

  • 图片数/集：该集完整消息历史中 image 块总数（mini：image_url 块；SDK：工具返回中的 image 块）。
  • 峰值 context/集：该集所有 LLM 调用中最大的一次输入上下文（全历史多轮下即末次调用）。
  • 数据源：outputs/beta-react-harness/std_mini_qwen3.5-4b_{bare,wp}/raw/episode_*.traj.json（各 100 集）；outputs/beta-coding-agent/sdk_{bare,wp}_claude-sonnet-5_fine_subset/raw/episode_*.jsonl（50/100 集）。
