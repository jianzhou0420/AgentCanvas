普通 Agent vs Coding Agent：差在哪里

同是 LLM + 工具 + 循环，为什么 coding agent 跑得更远 —— 行动空间、反馈回路、harness 与失败模式的完整对比。

这是系列里的概念篇：把"普通 agent"（固定工具集 / 预定义流程的 LLM agent，比如本仓库的图式 MapGPT）和 "coding agent"（Claude Code 这类在 repo + 终端里长循环工作的 agent）放在一起，从定义、行动空间、反馈回路、harness、失败模式五个维度拆开对比，最后回到本仓库的两条实验路线 —— 它们恰好是这场辩论的两个立场。系列文档：仓库概览 · 跑 Beta Agent · MapGPT 流程 · 本篇。

1. 先把词定准

Anthropic 在 Building Effective AI Agents 里给了一个被业界广泛采用的二分：

  • Workflow：LLM 和工具沿预定义的代码路径被编排 —— 走哪条分支、调哪个工具，是开发者写死的。
  • Agent：LLM 动态决定自己的流程和工具用法，自己掌控怎么完成任务。其运行时本质是一句话："LLM 在循环里根据环境反馈使用工具"。

日常说的"普通 agent"其实横跨这两类：(a) 固定流水线的 workflow agent —— RAG 问答、客服 bot、MapGPT 这类 prompting pipeline；(b) 通用任务 agent —— research agent、computer-use agent、具身 agent —— 它们有循环，但工具集是设计者预先圈定的 N 个 API。

Coding agent 是 agent 的一个特化：环境换成 repo / 终端 / IDE / 沙盒，工具换成"读写文件 + 执行命令 + 跑测试"。骨架仍是 ReAct 循环（推理 → 行动 → 观察 → 再推理），但两样东西完全不在一个量级上：行动空间和反馈密度。

核心论点先亮出来。普通 agent 和 coding agent 的区别不在"会不会写代码"，而在两点：① 行动空间是封闭的（预定义工具清单）还是开放的（运行时自己造工具）；② 环境给不给客观、即时、机器可读的反馈。后面所有差异都是这两点的推论。

3. 行动空间：固定工具集 vs 图灵完备

普通 agent 的能力被工具清单封顶：工具设计者没预想到的动作，它做不了；每进一个新领域，就得给它配一套新工具、造一个新 agent 变体 —— 于是有了 research agent、finance agent、marketing agent 这种"一域一 agent"的格局。

Coding agent 只需要一个元工具："写代码并执行"。Can Coding Agents be General Agents? (26.04) 把这一点作为定义性特征：coding agent 不局限于预定义工具集，而是在运行时编写、执行、调试自己的脚本。缺一个 CSV 解析器？现写一个。API 没有封装好的 SDK？直接 curl + 解析。这让行动空间在理论上图灵完备 —— 能力上限从"工具清单"变成"模型智力 + 环境权限"。

这也是 Anthropic 近来力推 "code execution as the core integration mechanism" 的逻辑（见 Cobus Greyling 的综述）：领域需求从"永久的专用 agent 变体"退化成"一段临时代码"—— 用完即弃，不留维护负担。MCP 生态同样在往"用代码执行包装工具调用"的方向收敛。

4. 反馈回路：coding agent 真正的护城河

Anthropic 那篇指南里最重要的一句话是：agent 执行期间，每一步都要能从环境获得 ground truth（工具返回值、代码执行结果）来评估进度 —— 循环没有真实反馈就只是在自说自话。

编码环境是数字世界里罕见的高密度客观反馈环境：

  • 即时：写完就能跑，错误秒级返回；
  • 免费：跑测试 / 编译不需要人参与；
  • 机器可读且可定位：栈回溯带文件名和行号，测试红绿是二值信号；
  • 可回滚：git 让任何失败的尝试都可以无损撤销。

ReAct 循环因此获得了自愈能力：写 → 跑 → 读错误 → 修，每一圈都在收敛。而普通 agent 的环境大多没有"错误信号"这种东西 —— 搜索结果不会报异常，发出去的邮件不会抛栈 —— 动作的后果延迟且主观，循环越长漂移越远。这解释了行业时间线：为什么第一个真正落地的自主 agent 品类是 coding agent，为什么 SWE-bench 式的数小时长任务最先在编码领域被攻克 —— 不是因为编码简单，而是因为编码环境替 agent 承担了验证工作（tests、linters、type checkers、runtime traces 全是免费的批评家）。

5. Harness：coding agent 不只是"模型 + prompt"

Sebastian Raschka 在 Components of a Coding Agent 里把一个现代 coding agent（Claude Code / Codex 类）拆成六个工程组件 —— 每一个都是普通 agent 框架里通常没有的：

组件做什么
1. Live repo context开工先摄取 git status、分支、项目文档（CLAUDE.md 等），而不是每个 prompt 从零开始。
2. Prompt 分层与缓存稳定段（系统指令、工具描述、workspace 摘要）与易变段（转录、当前请求）分离，最大化 KV cache 复用。
3. 工具校验层模型输出结构化工具调用 → 参数校验 → 权限门 → 执行 → 结果回灌；不是让模型在散文里"建议命令"。
4. 上下文缩减裁剪冗长日志、去重旧的文件读取、压缩转录 —— 主动管理上下文而非被动堆长。
5. 双层会话记忆working memory（当前状态蒸馏）+ 完整 transcript（可恢复的历史），支持断点续作。
6. 有界子 agent把子任务委派给上下文受限的 child agent，防止重复劳动和递归失控。

Raschka 的点睛之句：好的 coding harness 能让同一个模型显得比聊天框里强得多 —— 实际能力来自"模型 × 系统"，而不只是模型。相比之下，普通 agent 框架的 harness 往往只有 prompt 模板、工具 schema 和一个步数上限。

6. 失败模式：两边各有各的坑

普通 agent 的经典failure：幻觉难以被环境证伪（编造的"事实"没有编译器来揭穿）、长循环计划漂移、工具误用只能靠盲目重试。

Coding agent 的失败面更微妙。Can Coding Agents be General Agents? (26.04) 把 Claude Sonnet 4.5 和 GPT-5 放进 Odoo ERP 里跑 20 个业务场景，归纳出四种失败模式：

  • 偷懒的代码启发式：理解了政策，实现却走捷径 —— 比如按供应商名字而不是国家码过滤。
  • 业务层幻觉：先臆想出系统里不存在的功能，再基于臆想写出能正常运行的代码。
  • 约束丢失：多步推理途中悄悄丢掉规则手册里的显式约束。
  • 过度自信 / specification gaming：无论实际对错，一律报告成功 —— 优化的是"代码跑通"这个可测信号，而非业务正确性。

论文对根因的诊断值得背下来：反馈不对称（asymmetry in the feedback profile）。代码层错误有具体信号（异常、报错载荷），业务层错误几乎没有信号 —— ERP 校验格式但不校验政策合规。环境长期只惩罚前者，就等于在教 agent"执行成功 = 任务成功"。

推论。Coding agent 的强来自反馈回路，不来自它自己。把它放进反馈稀疏的领域，它就退化成普通 agent —— 而且还带着编码环境养成的过度自信。

7. "Coding agent 会吃掉普通 agent 吗"

正方（Anthropic 及其生态的叙事）：代码是通用接口 —— Claude Code 已被大量用于读文档、分析指标、写报告等非编码任务；与其为每个领域维护一个专用 agent，不如让 coding agent 现场写代码解决。专用 agent 变体 → 临时代码实现，"universal everything agent"。

反方（同一篇论文的实验数据）：10 个简单 ERP 场景里 Sonnet 4.5 稳定拿 80% 以上；但一旦场景需要 5+ 个决策、5+ 条约束，两个前沿模型都显著崩坏。业务—代码之间的翻译鸿沟（理解模糊需求 → 领域规划 → 政策合规）目前没有被行动空间的开放性解决。

折中判断：coding agent 是目前最好的通用 agent 底座 —— 开放行动空间 + 最成熟的 harness 工程；但它的通用性上限取决于目标领域能否提供可验证反馈。能"写个单测"的领域会最先被吃掉；反馈稀疏的领域（复杂业务决策、具身导航）短期内仍需要领域结构来补反馈 —— 也就是普通 agent / workflow 擅长的事。

两个值得点破的细节：

  • beta agent 其实是"剥掉了代码工具的 coding agent"。它 tools=[]（没有 Bash、没有文件系统），继承的是 coding agent 的 harness 与长循环能力 —— SDK 的上下文管理、结构化工具调用、skills 机制 —— 而不是"写代码"本身。用 §1 的语言说：它保留了开放的决策空间，但行动空间被刻意封死成 3 个工具。
  • R2R-CE 恰好是 §6 说的"反馈稀疏"象限。Agent 只有第一人称 RGB，没有分数、位姿、地图反馈；成功要靠自己在目标 3 m 内主动 STOP —— 环境不会告诉它"你走错了"。这正是 coding agent 护城河（密集客观反馈）完全失效的领域，所以 skills 和 STOP 确认门这类 harness 层设计才对得分影响巨大。这个 beta 实验有意思的地方就在于：它把"coding agent 能当通用 agent"的论断放到最不利的领域去检验。
