Agent 工程内幕：MCP、Harness 与 Skill 自进化

这一页面向"熟 VLN、想学 agent 工程"的读者：把 beta-coding-agent 整个技术栈从下往上拆开讲——MCP 到底是什么、为什么这里必须用它、harness/SDK 的每个旋钮为什么这么拧、driver 的工程陷阱，以及三个导航 skill 是怎么被"爬山"出来的。所有内容都以本仓库的真实代码为据，引用处标了文件位置。

关键读法：闭源的两层（模型 + CLI harness）是"被测系统"，开源的三层（driver、bridge、env）是我们造的"测量仪器"。仓库里写的代码只有两类角色——把环境包装成 agent 能说的语言（bridge，即你问的 MCP），和在 agent 外面主持实验（driver）。agent 循环本身一行都不归我们写，这正是 "vanilla coding agent" 主张的由来。

2 · MCP 是干什么的

2.1 理论：它解决 M×N 集成问题

MCP（Model Context Protocol，Anthropic 2024 年开源的协议）解决的问题很朴素：M 个 agent 应用 × N 个外部系统，如果每对都写一次胶水，就是 M×N 份集成代码。MCP 把它变成 M+N：任何实现了协议的 agent（host）都能用任何实现了协议的工具服务（server）。三个角色：

角色职责在本仓库里是谁
Host运行 agent 循环的应用，决定何时调工具claude CLI（被 SDK 无头拉起）
Clienthost 内部与某一个 server 的连接对象，1:1CLI 内部，对我们不可见
Server暴露能力（tools / resources / prompts）的服务mcp_bridge.py，每个 session 被拉起一个进程

协议底座是 JSON-RPC 2.0，传输层可选 stdio（本仓库用的：server 是子进程，走 stdin/stdout）或 HTTP/SSE（远程 server）。生命周期三步：initialize 握手（协商版本与能力）→ host 发 tools/list 拿到工具清单（名字 + 描述 + JSON Schema 入参）→ 之后每次模型想用工具，host 发 tools/call。工具清单会被 host 转译进发给模型 API 的 tools 数组——所以工具的描述文本本质上是 prompt 的一部分，每个请求都随行（靠 prompt cache 摊薄）。

2.2 线缆上长什么样

模型决定调用 observe 时，CLI 向 bridge 的 stdin 写一行：

{"jsonrpc":"2.0","id":7,"method":"tools/call",
 "params":{"name":"observe","arguments":{}}}

bridge 执行后从 stdout 返回内容块列表——MCP 原生支持图像块，这是 VLN 能接上的关键：

{"jsonrpc":"2.0","id":7,"result":{"content":[
  {"type":"image","data":"iVBORw0KGgo…(base64 PNG)","mimeType":"image/png"},
  {"type":"text","text":"{\"clearance_m\":{\"left\":6.3,\"center\":16.4,\"right\":30.2},…}"}
]}}

CLI 把它包装成 tool_result 塞进下一条发往 API 的消息。工具的对外全名是 mcp__env__observe——三段式 mcp__{server别名}__{工具名}，其中 env 是 driver 在 mcp_servers={"env": …} 里起的别名。

2.3 为什么这里必须用 MCP，而不是让 agent 直接发 HTTP

  1. 这是 stock harness 唯一的原生扩展点。实验主张是"不改 agent 一行代码"，那么接工具只能走它本来就会说的协议。MCP server 的配置只是 ClaudeAgentOptions 里的一个字典（command + args + env），CLI 自己完成 spawn、握手、schema 注入。
  2. 工具面即实验控制面。agent 能做的动作 = 注册的工具，一个不多。这是反作弊边界：评测函数 env_habitat__evaluate 和 observe/step 挂在同一个 auto_host HTTP 服务上，如果给 agent 留着内置 Bash 工具，它一条 curl 就能查到自己的 SR/SPL 甚至 oracle 传感器。所以 driver 设 tools=[]（关掉全部内置工具），agent 与世界的全部接口就只剩 bridge 里注册的两三个动词。run_episodes.py:313
  3. 描述即 prompt，schema 即约束。step(actions: list[int]) 的类型标注由 FastMCP 自动转成 JSON Schema，模型给错类型会在协议层被弹回；工具描述里写的"STOP 永久结束 episode、只在 3 米内发"是 agent 每一步都看得见的行为规范——比塞在 system prompt 里更贴近调用现场。

3 · Bridge 的工程细节（beta-coding-agent/mcp_bridge.py）

bridge 是个 ~370 行的 FastMCP 程序，但它浓缩了一批很典型的 agent 工程决策：

3.1 一个进程 = 一个 session = 一集

Agent SDK 每开一个 session 就 spawn 一个新的 bridge 子进程，所以每集的状态（步数、STOP 门、预算计数）直接放模块级全局变量就是安全的——进程隔离天然保证集与集之间零泄漏，session 结束进程即死。这是"用操作系统做状态管理"的偷懒美学：没有数据库、没有清理逻辑、没有串台可能。配置则走环境变量通道（HABITAT_SERVER_URL、HABITAT_TURN_BUDGET、HABITAT_BARE…），因为 MCP server 的启动参数就是 driver 在 options 里声明的 env 字典。

3.2 四个"调出来的机制"，各对应一个观测到的失败模式

机制针对的失败模式实现要点
look_around()
代码注释标明"iteration 2"		15° 一格地原地磨蹭、路口漏看方向一次工具调用换 4 个带标签视图（各 90°），转满 360° 后精确还原朝向；图像降采样到 384px 以免单条 MCP 消息过大
clearance_m 深度读数单目 RGB 距离错觉（"看着就在跟前"实际 4 米）从 raw depth 取眼高带（40–65% 行），左/中/右三分区各取 10 分位，输出米制数字——把像素变成模型算得动的量
turn-budget 广播不知道自己会被 harness 掐死，磨到超时得 0 分driver 的 max_turns 经 HABITAT_TURN_BUDGET 传进来，每次 step 结果回报 used/remaining；剩 ≤20 和 ≤10 时注入两级 BUDGET_WARNING 命令式警告
STOP 确认门"近失误急停"——冲到差一点的位置就宣布到达预算充裕时（剩余 >15 调用）第一次 STOP 被扣下，返回一段核对协议（look_around、逐词重读最后一个从句、放置规则），再发一次才执行；预算临界时门自动打开，绝不挡"抢救性停车"

这张表是本页最重要的方法论：agent 工程 = 把轨迹里反复出现的失败模式，编译成环境可供性（affordance）、harness 配置或 skill 文本三者之一。四个机制都属于第一类。

3.3 三个踩过的坑（都写进了代码注释）

  • allowed_tools 挡不住已注册工具。driver 跑在 permission_mode="bypassPermissions" 下，此时模型对任何已注册的 MCP 工具都可直接调用，把 look_around 从 allowed_tools 里删掉没用——唯一可靠的门是压根不注册（bare 模式下 if not BARE: mcp.tool()(look_around)）。教训：权限层是 UX 概念，能力面才是安全边界。mcp_bridge.py:264-269
  • stdout 缓冲区会咬人。look_around 一条消息带 4 张图，超过 SDK 默认 1 MiB 的 stdout 缓冲上限，消息被截断、session 解析中途暴毙。修法是 options 里 max_buffer_size=32MiB。stdio 传输的代价：所有字节都挤一根管子。run_episodes.py:336-338
  • 描述文本必须随机制一起切换。BARE 模式不只删机制，连 observe/step 的描述都换成不提 clearance、不提确认门的版本——否则模型会按描述去等待一个不存在的行为。工具描述是接口契约，撒谎会直接改变 agent 行为。mcp_bridge.py:62-90

4 · Harness 与 SDK：每个旋钮为什么这么拧

driver 用的是 claude-agent-sdk（Python）。它本身不含模型循环——它把参数翻译成命令行旗标，spawn 一个捆绑的 claude CLI 子进程（…/site-packages/claude_agent_sdk/_bundled/claude），用 stream-json 协议在 stdin/stdout 上收发结构化消息。真正的 agent 循环（采样、工具路由、上下文管理、重试）全在 CLI 里，闭源。ClaudeAgentOptions 是我们对这个黑盒仅有的控制面，本仓库每一项的取值都带着一个被验证过的理由：

Option取值为什么（含事故记录）
system_prompt自写导航简报（整体替换 CLI 内置 persona）把任务、工具语义、3 米成功判据、"自主工作到 STOP"写死。opus-lab 另有 --builtin-system-prompt 模式：保留 CLI 内置 Claude Code persona，简报改作第一条用户消息——专测"原味 coding agent 人格"的对照组
tools=[]关掉全部内置工具纯 ReAct over env；也是 §2.3 的反作弊边界
setting_sources=[]不加载任何文件系统配置否则 CLI 从 cwd 向上爬找到仓库的 CLAUDE.md 注入每个 session——除 token 开销外还有行为污染（2026-07-05 实录：session 开始用项目自定义的 "Heard as:" 回复惯例）
strict_mcp_config=True只用 driver 声明的 bridge否则继承 ~/.claude 里用户的全部 MCP server（Gmail、x-mcp…），既污染 vanilla 主张，又在并行开 session 时挤占 bridge 的连接窗口
allowed_toolsbridge 的 2–3 个工具bare 时不含 look_around（配合 §3.3 的注册门控）
permission_mode"bypassPermissions"无头跑批不能有人点确认；代价见 §3.3 第一条
max_turns=100harness 级预算真正会杀 session 的死线；经 TURN_BUDGET 广播给模型（§3.2）
max_buffer_size=32MiB放大 stdout 缓冲§3.3 第二条
cwd=workdir_i每集独立空目录session 的文件系统视角与仓库隔离
model / betas按实验传入betas 直通 API beta 头，如 interleaved-thinking-2025-05-14

4.1 Thinking 配置是分模型家族的（一个真实调试故事）

Claude 4.6+/5 系模型（opus-4.6+、sonnet-5、fable-5）用 {"type":"adaptive","display":"summarized"}——模型自己决定何时思考，SDK 拿到的永远只是思考摘要（raw CoT 不出 API）。而 haiku-4.5 这类 pre-4.6 模型不认识 adaptive：传了等于把 thinking 悄悄关掉。2026-07-07 的验证记录写在代码注释里：haiku 整集只出 ~1 个 thinking block（且都在第一轮，因为它也不支持 interleaved thinking——工具结果之后不再思考），对照 sonnet 的 ~35 个；haiku 被迫把整个"账本"外化到可见文本里。修法：haiku 走 {"type":"enabled","budget_tokens":4000}，interleaved 思考需要 beta 头显式开启。run_episodes.py:272-292 这个故事的一般教训：harness 参数在不同模型上语义不等价，"同一配置跑三个模型"并不是天然公平的对照——必须逐一验证行为。

4.2 认证：一个会悄悄换账单的陷阱

无头模式下，环境里若残留 ANTHROPIC_API_KEY，计费会静默从订阅切到 API。两个 driver 都在启动时防御性地 os.environ.pop("ANTHROPIC_API_KEY")，运行时再加 env -u ANTHROPIC_API_KEY 双保险。

5 · Driver：agent 外面的实验主持人（run_episodes.py）

  • 每集一个全新 session = 记忆归零的实验设计。没有跨集学习、没有残留上下文，每集都是独立同分布的试次。episode 的"记忆"就是 session 的上下文窗口本身（见 §6）。
  • 考官与考生分离。摆放（/env-panel/field/episode_index → play → reset）、读指令、评测（env_habitat__evaluate）全部走 driver 自己的 HTTP 客户端，不经过 bridge——agent 从工具面上就不可能看到 SR/SPL、位姿或 oracle 传感器。
  • 一个真实的竞态：CLI 起跑比 MCP 握手快。并行开多个 session 时，模型第一轮推理稳定地跑在 bridge 连上之前，看到"零工具"就开始瞎答。修法：先 get_mcp_status() 轮询（60 次 × 0.5 s）等 bridge 报 connected，再发第一条 prompt。run_episodes.py:394-413
  • 并发模型：一个 auto_host = 一个 worker（模拟器是有状态的，不能两集共用），asyncio 队列领活，worker 按位次错峰 2 s 启动（避免 session spawn 风暴），每集 asyncio.wait_for 包 2400 s 超时；单集异常/超时记为 error 记录，绝不炸整个 run。阻塞的 HTTP 全部 asyncio.to_thread（冷服务器首次 play 载场景要 ~30 s）。
  • 双流日志。curated 流 episode_{i}.jsonl（前端 Monitor 喂食用：episode_meta / session_inputs / thinking / assistant_text / tool_use / tool_result / result / episode_metrics，每事件即时 flush 供 tail -f）+ raw 流 raw/episode_{i}.jsonl（每条 SDK 消息全字段落盘，base64 图像块按"超 4000 字符且无空格"启发式抹除）。session_inputs 事件甚至把 bridge 的工具 schema 在进程内 import 后原样抓拍进日志——轨迹文件因此是完整的 I/O 复现记录：喂给模型的每个字节和它吐出的每个事件都在。
  • 成本核算免费送。session 结束的 ResultMessage 自带 usage（input/output/cache_read tokens）、total_cost_usd、num_turns、duration——ECCV 报告 5.3 节的成本表数据源就是它。

6 · 理论串讲：这套系统里的 agent 概念

  • ReAct 循环。观察→推理→行动→观察，是 2022 年 ReAct 论文的范式；coding agent 的"读文件→思考→改代码→跑测试"和这里的"observe→思考→step→observe"是同构的。本实验的全部意义在于：这个循环的实现不是我们写的，是 CLI 里那个为软件工程调出来的闭源循环。
  • 上下文窗口 = 工作记忆。这里没有外挂记忆（无 RAG、无数据库、tools=[] 连文件系统都没有），agent 唯一的记忆就是对话上下文。ledger-nav skill 的三条公理精确刻画了这个设定的独特之处：① 动作是米制的，位置可以用算术自己推（航位推算）；② 看过的每一帧都还在上下文里，所以不需要"描述并存储"，只需要一个能翻回去重看的索引；③ 可以验证——每次移动是一次变更，每次观察是一次测试。这是长上下文多模态模型才成立的前提，GPT-4V 时代的 VLN prompting（描述完就丢帧）不具备。代价同样真实：100 轮 × 每轮一到多张图，上下文以图像速度膨胀，CLI 的自动压缩（closed）何时触发、压掉什么，我们观测不到——这是"闭源 harness 上做科研"最扎手的不可控项。
  • 把隐形死线变成环境状态。max_turns 是 harness 的处决线，但模型天生看不见它。turn-budget 广播的设计哲学：与其要求模型自己数拍子，不如把预算做成每次工具调用都回显的环境状态——认知负担从"记住"降为"读取"。两级警告则是升级协议：剩 20 提醒收敛，剩 10 直接下命令。
  • STOP 确认门 = 给不可逆动作加二次确认。这和 Claude Code 对 rm -rf 弹确认是同一个交互设计模式：不可逆 + 高价值的动作，第一次请求返回一个核对清单而不是执行。区别在于这里的"确认对话框"是环境返回的文本，确认者是模型自己。
  • 感知的文本化（perception grounding）。clearance_m 和 opus-lab 的 3×3 深度网格做的是同一件事：把模型不擅长的（从单目像素估米数）预计算成它擅长的（读数字、做算术）。工程上就是几行 numpy 分位数，效果上补的是多模态模型的系统性短板。

7 · Skill 与"自进化"

7.1 Skill 是什么、在这里怎么注入

Claude 生态里的 skill 是一个带 YAML frontmatter 的 SKILL.md：name + description（供按需检索）+ 正文（做事的方法论）。CLI 原生的 skill 系统靠文件系统发现、按需加载——但本实验 tools=[] 且 setting_sources=[]，agent 摸不到文件系统，所以 driver 走了更可控的路：读 SKILL.md、剥掉 frontmatter、用 <skill name="…"> 标签拼进 system prompt。run_episodes.py:587-594 这个选择保证 skill 是一个纯粹的实验变量：字节级可记录（session_inputs 里有完整快照）、无加载时机的不确定性。

三个 skill 是三种"导航算法作为文本"的范式，同一接口下可互换对比：

Skill算法范式核心机制
ledger-nav状态估计 + 簿记航位推算里程计（左转 +15°、前进 0.25·cosθ，自己做算术）、帧账本（索引而非复制历史观察）、predict-execute-verify、保证终止的 STOP 协议——"像写代码一样导航"
mapgpt-nav拓扑地图MapGPT（arXiv:2401.07314）的五记忆块移植：Trajectory / Map（"Place i is connected with Places j,k" 原格式）/ Supplementary（见过未去 = 回溯目标）/ Planning / Progress，每条回复必须复述更新——上游靠模拟器给候选 viewpoint，这里 Place 由 agent 在决策点自己创建
opus-nav决策规则（无簿记）面向强模型：把指令编译成"逐从句 DONE-test"，每步自报完成度，STOP 由里程计而非眼睛把关

7.2 "自进化"的真实机制：debug 驱动的爬山

skill 不是一次写成的，也不是什么自动搜索算法跑出来的——它是一个人机协作的 hill-climb 闭环，把"调 prompt"过程做成了受控实验。整个方法论都成文在 opus-lab/README.md 的 "Hill-climb discipline" 一节：

┌────────────────────────────────────────────────────────┐
│ ① 跑：driver.py --episodes 0-9 --skill opus-nav        │
│ ② 读：episode_{i}.jsonl —— thinking/工具调用逐帧回放   │
│ ③ 诊断：失败归因到一个可命名的行为模式                 │
│    （例：'叙事式完成'——嘴上说到了，人还差 3 米）       │
│ ④ 改：往 SKILL.md 里加/改【一条】discipline            │
│ ⑤ 重跑同一批 episodes                                  │
│ ⑥ keep-if-better / rollback-if-worse ──→ 回到 ①        │
└────────────────────────────────────────────────────────┘

三条纪律让它成为科学而不是炼丹：

  1. 只动 skill。环境冻结在 bare 工具对上——SR 的变化才能归因给 skill 而非 harness。这正是 opus-lab 存在的理由：老 driver 的 --bare 把"env 机制存在与否"和"有无 skill"焊死在一起（bare ⇒ 无 skill），永远跑不了"bare 工具 + skill"这个爬山必需的条件，于是干脆另建一个从构造上就解耦的清洁室。
  2. 不准背答案。skill 只能教方法，不得含任何来自具体 episode ground truth 的事实（布局、路长、终点长相）；举例必须虚构，严禁从跑过的轨迹里抄——否则爬山爬进测试集，分数就成了泄漏。
  3. 敬畏方差。n=10 的 SR 方差是 ±0.1，单集的涨跌不构成证据，不许过度解读。

进化的痕迹直接写在 skill 的 frontmatter 里——opus-lab 版 opus-nav 的 description 就是一份 changelog："grown one discipline at a time. v6 = 逐从句几何 DONE-test + 每步完成度追踪 + 有序过闸 + 里程计把关的停车（带过冲）……它对抗的是 agent '嘴上把路线讲完、人还站在几米开外'的习惯……后续 discipline 继续加进这同一个 skill"。v6 的四条纪律，每一条都能对回 ③ 里的一个具体失败模式。

两条谱系 + 一块化石 仓库里有两份 opus-nav：skills/opus-nav（152 行，配老 driver 的全机制环境，走"四决策规则"路线）和 opus-lab/skills/opus-nav（87 行，v6，爬山主线）。另注意 opus-lab 的 README 还写着 bridge "只有 RGB observe + step"，但 bridge.py 实际已进化成"标准 VLN-CE 观测集"（RGB-D、3×3 米制深度网格、位姿、里程计、内参、8×45° 全景）——文档滞后于代码，恰好是进化过程留下的地层剖面。其辩护逻辑写在 bridge 的 docstring 里：这些正是任何监督式 VLN-CE agent 都拿得到的输入，而 oracle 传感器（最短路、进度）被刻意不转发。

7.3 更宏观地看：环境也曾进化，后来被冻结

把时间线拉长，这个项目其实做了两轮进化：第一轮进化的是环境接口——共享 bridge 的四个机制（look_around 注释里就标着 "iteration 2"）每个都是从失败轨迹里长出来的；第二轮开始前，作者意识到环境和 skill 两个变量纠缠会毁掉归因，于是冻结环境、只留 skill 一个自由度。这个"先探索、后冻结、再受控爬山"的节奏，就是 agent 系统调优的标准姿势——和调神经网络先扫超参再固定 seed 做消融是同一个思维。
