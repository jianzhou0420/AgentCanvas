Coding Agent as Navigator — ECCV Workshop 技术报告骨架

这一页是和原作者合写 technical report 的写作规划：故事怎么讲、每一节写什么、还缺哪些实验、审稿人会打哪里。所有 【填】 都表示需要跑实验或去原论文核对的数字——本页刻意不编造任何数值。

现状（2026-07-11） 管线已端到端验证（episode 摆放 → reset → observe 渲染 → evaluate 出分都通了），但还没有任何一集完整跑分。7-11 那次 UI run（ui_20260711_151635）在第一次 observe 之后就停了，没有 summary。所以论文里"我们的"每一个数字目前都是空的——实验矩阵见 §6。

1 · 一句话定位与贡献分层

核心命题：不为导航做任何具身特化，把一个现成的商用 coding agent（Claude Code harness，经 Agent SDK 无头驱动）通过两个工具接进 Habitat 连续环境，它在 R2R-CE 上能走到什么水平？分数里有多少来自模型、多少来自脚手架（harness）、多少来自我们额外注入的导航算法？

一段话 pitch 草稿：

现有 zero-shot VLN 方法都在为 LLM 手工搭建导航专用脚手架——waypoint 预测器、全景摘要、拓扑图 prompt。与此同时，工业界已经把迄今最强的通用 agent 脚手架造了出来（coding agents），只是没人拿它去导航。我们把一个未改动的商用 coding agent 接上最小接口（egocentric RGB + 四个离散动作原语，无位姿、无地图、无候选点），在 R2R-CE val-unseen 上测量它的导航能力，并通过正交消融分解"模型 / harness 机制 / 环境接口机制 / 文本注入的导航算法"各自的贡献。

贡献可以分三层叙述（建议 A 为主线，B、C 做支撑——workshop 短文只讲一条主线）：

层叙事对应素材
A · 能力测量（measurement study）Stock coding agent 在最苛刻接口下的 VLN-CE 零样本成绩 + 完整成本核算（token / 时间 / 美元）rand100 主实验，raw JSONL 里的逐轮 usage
B · 变量分解四个变量正交消融：模型档位 × harness 特性（thinking、内置 system prompt）× env 机制（look_around / clearance / STOP gate）× skillopus-lab/ 清洁室正是为此设计的（bare 工具 + 可叠加 skill，互不纠缠）
C · skill 即算法把导航方法重写为纯文本 skill（ledger-nav / mapgpt-nav / opus-nav），同一模型同一接口下公平对比 prompting 方法beta-coding-agent/skills/*/SKILL.md

2 · 为什么这个故事站得住：和既有 zero-shot VLN 的差异

方法环境感知接口动作接口导航专用组件
NavGPT / DiscussNavR2R（离散）视觉→caption 文本模拟器候选 viewpointcaption 模型、候选点
MapGPTR2R（离散）全景 + 候选标注候选 viewpointprompt 内建拓扑图
Open-NavR2R-CE（连续）BLIP-2 场景描述waypoint predictorwaypoint 模型 + 描述模型
SmartWayR2R-CE全景增强 waypoint predictorwaypoint 模型 + 回溯机制
Ours（bare）R2R-CE单帧 egocentric RGB0=STOP · 0.25 m · ±15°无——脚手架是通用商用 harness

四个差异点，Intro 里逐个立起来：

  1. 接口最苛刻。没有 waypoint predictor、没有 caption 模型、没有全景（bare 模式）、没有位姿——比表里每一个 baseline 拿到的信息都少，动作还是低层原语。任何正分都说明问题。
  2. 脚手架是通用的，不是导航专用的。这是与所有既有工作的本质区别：我们不设计脚手架，我们测量一个为写代码而生的脚手架。
  3. 首次量化 "harness contribution"。vanilla 分数 = 模型 + 闭源 scaffolding；bare / 换 system prompt / 关 thinking 的对照能把这层剥出来。
  4. 长上下文改变了前提。ledger-nav 的三条公理（动作是 metric 的、每一帧都还在上下文里、可以验证）在 GPT-4V 时代的 prompting 方法里不成立——"帧索引而非帧描述"是新范式，值得单独一小节。

3 · 标题与摘要草稿

候选标题（按我推荐排序）：

  1. Coding Agents are Zero-Shot Vision-and-Language Navigators —— 最直接，蹭认知。
  2. The Scaffold Is the Navigator: Dissecting a Commercial Coding-Agent Harness on VLN-CE —— 突出 B 线（分解）。
  3. From Terminal to Hallway: Measuring the Embodied Competence of a Stock Coding Agent —— 有记忆点，稍文艺。
  4. Coding Agent as Navigator（主标题）+ 副标题任选 —— 保底方案，和 repo 叙事一致。

Abstract 逐句功能骨架（150–200 词）：

句功能草稿要点
1背景反差zero-shot VLN 在造专用脚手架；通用 agent 脚手架已经存在，无人用于导航

4 · 逐节骨架

§1 Introduction（约 1 页）

  • 钩子：两条线各自狂奔——VLN 的手工脚手架越造越重；coding agent 的通用脚手架越造越强。交点无人踩过。
  • 三个研究问题：RQ1 走不走得动（vanilla 成绩）；RQ2 分数从哪来（模型 vs 脚手架分解）；RQ3 纯文本注入导航算法还能涨多少（skill）。
  • 贡献 bullet 四条 = §1 的三层 + 开源（driver/bridge/skills/轨迹全开源，评测是 habitat 原生 ruler）。
  • Figure 1：系统图（见 §7 图表清单）。

§2 Related Work（0.5–0.75 页，短文可压成一段）

  • (a) 监督式 VLN-CE：CWP-CMA、CWP-RecBERT、ETPNav 一句带过，只为表格提供上界参照。
  • (b) zero-shot LLM 导航：NavGPT → MapGPT → DiscussNav → Open-Nav → SmartWay/InstructNav，按"脚手架越来越重"的线索排，落点是"我们反其道"。
  • (c) 通用 agent harness：SWE-agent 类、computer-use、Agent SDK / MCP 生态。落点：这些系统的能力测量目前只在软件任务上做过。

§3 System（1–1.5 页，原作者主笔）

  • 3.1 接口与"vanilla 纪律"：observe/step 语义表；README 里的 deliberate v1 choices 直接改写成设计原则三条（tools=[] 无内置工具、单帧 egocentric、agent 必须自己 STOP 否则按预算耗尽处诚实计分）。
  • 3.2 架构：driver（摆放/评测）↔ MCP bridge（每集一进程）↔ headless CLI ↔ auto_host env。强调职责分离：agent 看不到位姿、深度、奖励、度量；订阅计费、每集全新会话（无跨集记忆）。
  • 3.3 变量正交化：主 bridge 的四个 env 机制（look_around、clearance_m、turn-budget 广播、STOP 确认门）与 skill 在旧 driver 里是纠缠的（bare ⇒ 无 skill）；opus-lab 从构造上解耦——bare 工具永远固定，skill 可独立叠加。这一段是 RQ2 实验合法性的根基，值得写透。
  • 3.4 Skills as navigation algorithms：三个 skill 各一段——ledger-nav（航位推算 + 帧索引 ledger + predict-execute-verify + 保证终止协议）、mapgpt-nav（MapGPT 五记忆块移植到无候选点的原语动作空间，注明改编自 arXiv:2401.07314）、opus-nav（无簿记，四条决策规则，面向强模型）。这是 C 线的正文。

§4 Experimental Setup（0.5 页）

  • rand100：R2R-CE val-unseen 的 100 集论文标准子集，与 Open-Nav/SmartWay 完全同款 ⇒ 其表格数字可直接搬来对比（搬运时逐格核对原文）。
  • 度量：TL、NE↓、OSR↑、SR↑、SPL↑（列与 Open-Nav 表对齐）。
  • 预算：max-turns 100 / step-budget 500 / episode-timeout 2400 s / think-budget 4000。
  • 版本钉死小节（必写，这是闭源系统上做科研的态度）：claude CLI 2.1.206、claude-agent-sdk 0.2.116、模型 ID（如 claude-opus-4-8）、实验日期窗口。闭源 harness 会静默更新——日期就是实验条件的一部分。

§5 Results（1.5–2 页，你主笔）

  • 5.1 主表：见 §5 mockup。
  • 5.2 消融：(a) env 机制阶梯 bare → +look_around → +clearance → +STOP gate；(b) 三个 skill × 最优模型；(c) thinking budget 扫描；(d) 内置 system prompt vs 替换（harness contribution 的直接证据）。
  • 5.3 成本：tokens/集（raw JSONL 逐轮 usage，含 cache_read 命中率）、墙钟时间、美元估算、SR-per-dollar。坦白报成本本身就是贡献——没有任何 zero-shot VLN 论文认真做过这个。
  • 5.4 行为分析：步数分布、自主 STOP 率、回溯次数、失败类型学（迷路 / 误停在 decoy / 预算耗尽 / 过早 STOP）——全部可从 episode JSONL 脚本化统计，不用人工标。

§6 Discussion（0.5–1 页）

  • 闭源 harness 的可见面与不可见面：zh-4 页那两张表（外部可观测组件 vs 合理推测的闭源内部）直接改写成论文小节 + Table 3。
  • 复现性协议：钉版本 + driver 侧全开源 + bare 对照剥离 scaffold + 公开全部轨迹 JSONL。定性为 "measurement study of a system that exists in the world"。
  • 数据污染：R2R 指令文本可能在训练数据里，但在连续环境低层动作接口下，"背答案"无法直接兑现为 15° 转角序列——这个论证要写严谨，并承认不能完全排除。

§7 Limitations & Conclusion（0.25–0.5 页）

  • 100 集、有限 seed 的方差；温度等采样参数不可控（闭源）⇒ 用 bootstrap CI 兜底。
  • 贵且慢，不是实时导航器——这是能力测量，不是部署方案。
  • 只测了 R2R-CE；RxR、EQA、真实机器人是 future work（可以顺势预告 AgentCanvas 2.0 的方向）。

8 · 审稿人攻击点与预案

攻击预案
"闭源 harness，不可复现"正面定性为 measurement study；钉版本 + 日期窗口；driver 侧全开源；bare 对照把 scaffold 剥出来单独计量；全部轨迹 JSONL 公开。
"rand100 才 100 集，太小"与 Open-Nav/SmartWay 同款子集，可比性优先；报 bootstrap CI；预算允许则补 E9 full split。
"R2R 指令在训练数据里，污染"低层动作接口论证（背文本换不来 15° 转角序列）+ 坦白无法完全排除 + 失败案例恰好说明没在背答案。
"又贵又慢，有什么用"研究问题是能力测量而非部署；成本表本身是贡献；顺势讨论蒸馏/本地化路线。
"这不就是 prompt engineering"opus-lab 的正交设计使 skill 成为受控变量；三个 skill 是三种算法（航位推算簿记 / 拓扑图 / 决策规则），有明确的机制假设和可证伪的预测。
"单次 run，方差呢"E8：主配置重复 2–3 次；采样参数不可控这一点如实写进 limitations，反而佐证"钉日期"协议的必要性。

9 · 投稿实务、分工与待对齐问题

  • 格式与页数：ECCV workshop 各自发 CFP，常见两档——与主会同格式的 full paper（LNCS，通常正文 14 页上限）或 extended abstract（4–8 页）。先选定目标 workshop 再定篇幅；本骨架按 full 规划，砍成短文时的刀口：§2 压成一段、5.4 与 Tab.3 进附录。
  • Archival 与否要查清楚：如果 workshop proceedings 是 archival 的，同一工作后续投主会可能受限——如果还想扩成主会论文，优先选 non-archival workshop。
  • 分工建议：原作者（系统设计者）主笔 §3 System + Fig.1；你主笔 §4–5（实验执行、统计脚本、成本核算）+ 复现包；§1/§6 共同打磨。
  • 相对时间线（从确定 workshop 起算）：第 1 周 E0 标定 + 排期；第 2–3 周 E1–E3 主实验；第 4 周 E4–E7 消融；第 5–6 周 写作 + 图表；第 7 周 内审 + 打磨 + 提交。E0 之后每一步都可能因订阅额度重排——所以 E0 必须最先跑。

和原作者第一次碰头要对齐的问题清单：

  1. 目标 workshop 是哪个？deadline、页数、archival 与否？
  2. 主线选 A（能力测量）还是 B（分解）？——决定标题和主表的组织方式。
  3. 订阅/算力预算：rand100 × 多少个配置跑得起？（E0 之后用数据说话）
  4. 是否公开全部轨迹 JSONL 和 outputs（涉及订阅账号信息脱敏）？
  5. 署名顺序与通讯作者。
  6. rand100 够不够，还是咬牙上 full val-unseen？
